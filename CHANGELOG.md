# Changelog

Notable changes, grouped per release. Every release tag `vX.Y.Z` ships the
browser agent bundle, the collector package, the inventory entry snippet, and
the Terraform modules together at that tag, so a user-facing change to any of
them lands with an entry under Unreleased in the same pull request.

## [Unreleased]

### Changed

- A repeat sighting in the collector now costs one DynamoDB write instead of two. Novelty is decided by a single `UpdateItem` upsert that returns the item's prior state (no prior item = first sighting, enqueued; otherwise the same write has already moved `last_seen` and `sessions`), replacing a conditional `PutItem` whose failure — still billed — was followed by a counter update on every repeat. The same first sightings reach the queue and the same counters move. The Lambda role's novelty grant drops `dynamodb:PutItem`.
- The collector emits its metrics as CloudWatch Embedded Metric Format log lines instead of a `PutMetricData` API call at the end of every invocation. Metric names, units, dimensions and the namespace are identical, so existing alarms, the Datadog monitors and dashboards keep their series; what changes is that the request path no longer makes a CloudWatch round-trip, there is no per-request API charge at beacon volume (log ingestion of a few hundred bytes per invocation replaces it), and the ingest role drops `cloudwatch:PutMetricData` — the one action on it that could not be resource-scoped. The comparator role keeps that grant for the canary heartbeat.
- The browser agent now remembers, per device, what it has already **reported**: a `localStorage` set (`__rum.seen.device`) stamped at transport handoff with the keys of the observations a beacon carried withholds an observation this browser reported within the last seven days, behind the existing per-session set. New content, a new initiator or a new script is a new key and reports at once; a first sighting whose beacon never left the device is reported next session if it is seen again (the stamp records a handoff, not a capture); inline scripts the client could not hash are deduplicated per session only, because their wire identity embeds source excerpts that must not persist; a stamp later than now — a clock that was ahead, or a value written by page code — reads as expired, so no stamp can suppress a key past the window; and the record is capped at 2000 entries and 128 KB, newest first. Storage disabled, full, private or corrupted degrades to per-session memory. A session with nothing new to report sends one health-only heartbeat (no DynamoDB write — agent-health is never keyed), so per-target accepted-beacon volume keeps its shape and the volume tripwire its baseline. The stamp records a handoff to the browser, which is all the agent can observe (the collector answers every outcome with the same empty 204): a beacon the browser queued and then lost, or that the collector refused, is withheld on that device for the window — so rotate the edge secret and add origins collector-first (see the adopter guide, step 9). **Behaviour change:** the novelty store's `sessions` prevalence counts device-weeks rather than visits, and a known URL that later arrives as parser-inserted markup (no initiator) is withheld for the window where it used to be for the session.

### Fixed

- A framed step's timeout now helps tell the two ways a frame can go silent apart. When a matching frame gives no answer, the monitor also asks Chrome directly, in the same window — in a fresh isolated world on that frame's own DevTools session, bypassing the automation library's record of the frame — and the timeout adds either that Chrome answered while the library got nothing (most likely the library's handle on the frame stopped answering, though a very slow renderer can look the same) or that the frame's renderer is not responding. A split card field timing out this way is a different failure from the frame-search starvation fixed in the next entry.
- A workflow step with `frameUrl` no longer times out on a field that was visible the whole time. The monitor searched the matching frames one after another, giving each a 100 ms wait; a wait in an out-of-process frame is several DevTools round trips into its renderer, so when a card provider's frames were busy (right after a complete card number goes in) on a contended runner, every attempt outlasted its slice, was cut off, and the step failed at its 120 s timeout. Split card fields — number, expiry and CVC each in its own frame at the same URL — hit this at the expiry or CVC step on roughly one scheduled run in three, and failed the target whenever both attempts starved. Each matching frame now gets one wait lasting the whole deadline, all in parallel, with frames that attach mid-wait picked up; an element still counts only if its frame's URL matches the anchored pattern once it is held. A framed step's timeout now also says, per matching frame, whether the selector was absent, present but not visible, visible, unreachable (the probe failed, e.g. the frame detached) or gave no answer, and the `Observed frame URLs` list counts repeated URLs (`url (×3)`) instead of listing them once.
- The collector's 90-day novelty window now rolls from the **last** sighting, as the specification always said (FR-009: a script absent from traffic for 90 days returns as a first sighting). The record's TTL was anchored to the first sighting instead, so a script continuously present on the page re-entered the queue as a "first sighting" — and alerted, or opened a candidate PR — every 90 days. **Behaviour change:** continuously present scripts no longer re-alert on that cycle; a script that genuinely disappears and returns after 90 days still does — including when it returns before DynamoDB has lazily deleted its expired record, which is read as no record and reset to the new sighting.
- The collector's compensating delete — which clears a first-sighting record whose SQS enqueue failed so a later delivery can re-enqueue it — can now actually run: the Lambda role never granted `dynamodb:DeleteItem`, and because the compensation is best-effort behind the always-204 contract the `AccessDenied` showed up only in the Lambda log while the record went on suppressing that observation for its 90-day TTL. The grant is added and asserted in the module's test suite.
- An `authoriseWith` alternative marked `"authorised": false` now denies whatever its matcher type. `nameMatcher`, `urlMatcher`, `hostMatcher`, `initiatorHostMatcher` and `contentMatcher` ignored their own flag, so in array syntax (or inside a composite) a pending or declined alternative of those types authorised whatever its pattern matched, as long as the entry's first alternative was approved; hash, CSP-directive, workflow and target-type alternatives always denied. **Behaviour change:** such an alternative now has to be approved (its own flag set to `true`) before it authorises anything; pending header values the inventory pass coalesces into one entry are approved per value.
- The attribution shim now records scripts inserted inside a `DocumentFragment` (a cloned `<template>` or parsed range), which read as parser-inserted — attributed to the page — and no longer records `insertBefore`'s reference node or the node `replaceChild` removes as inserted by the current script: the classic loader snippet inserts before the page's first `<script>`, which was being attributed to the loader.
- A script the page inserts through the DOM is now attributed, on the synthetic passes, to the script that inserted it. The monitor's own attribution shim wraps `appendChild`, so its wrapper — not the inserting script — was the top frame of every such request, and `Matchable.initiator` fell back to the page URL. **Behaviour change:** a synthetic `initiatorHostMatcher` now sees the inserting script's host, as the RUM agent always has; an entry written against the page host for a dynamically inserted script stops matching it (and alerts) until it names the loader's host. Parser-inserted `<script src>` tags are unaffected.
- Scripts loaded from `blob:` URLs are now rendered correctly everywhere a URL is redacted: the auditor report's `origin.url` read `https://hosthttps://host/<uuid>` and `origin.host` read `(unknown)` for every blob-loaded script, and an unanswered Turnstile blob request surfaced in the run summary looking like a malformed URL on the page. `redactUrl` keeps the `blob:` scheme and redacts the inner URL, and `extractHost` reports the minting document's host. The derived `rowId` of every row whose URL is a `blob:` URL — blob-loaded scripts, and any header row recorded from a `blob:` response — changes as a result (it is built from the redacted URL); no other row is affected, and the report schema is bumped to 1.6.1 to mark the derivation change.
- Scripts loaded inside a cross-site iframe — a card provider's hosted fields moving on to its 3-D Secure challenge — are now read and compared when the frame navigates itself away. The iframe runs in its own browser process, which the page-level body retention did not reach, so those scripts failed with `Could not load response body for this request` and turned the run red as unread. The monitor now asks every such frame to retain its response bodies too.
- A script request that never gets a response no longer marks the run partial or exits `2`. Chrome has been observed to report a script's response only once its body is complete, and the script cannot run before then, so an unanswered request — a malformed URL, a host that never answers, a frame torn down mid-request — never executed on the page. Two backstops keep that safe: a script whose body is seen to finish loading without a response surfacing (Puppeteer's `requestfinished`, or Chrome's own `Network.loadingFinished`) is recorded as unread instead, and so is a late response whose read never settles. Each is still listed, as evidence: `targets[].unansweredRequests` and `summary.requestsUnanswered` in the auditor report (schema 1.6.0; 1.5.0 listed them under `unreadScripts` with `status: 0`) and **Script Requests Unanswered** in the run summary. The run no longer spends its 15 s wait on requests from a frame that has already detached. A response that lands after all, as the browser closes, is still recorded as unread and still fails the run; a late 404 or 502 leaves the request listed, with that answer noted, and a late redirect hands it over to the script it redirects to. The run summary's lists of unread scripts and unanswered requests now show at most 20 rows each — one per affected target first — while still naming every further affected target, so no target with an unread script goes unnamed, and point at the auditor report for the rest, so a widespread outage cannot push the Slack summary past its 50-block limit and get it rejected. Failed targets and undelivered alerts are still listed in full.
- Scripts that finish loading as the payment page navigates away are now read and compared instead of silently dropped. Chrome discards a page's response bodies once a navigation away from it starts, so every script pulled in by a "Pay" click on its way to 3-D Secure failed with `Could not load response body for this request` and vanished from the run, which still exited 0. The monitor now asks Chrome to retain response bodies across navigation, waits for in-flight script requests and reads before closing the browser, and accounts for any script it still cannot read: each is listed in the auditor report (`targets[].unreadScripts`, `summary.scriptsUnread`; schema 1.5.0) and named in the run summary under **Scripts Not Read**, and one on the payment page marks the run partial and exits `2`, like a failed target. Unread scripts on earlier pages the payment page replaced are listed for evidence without changing the exit code.
- A required `content-security-policy` is no longer reported missing on a redirect response: CSP presence is now checked only on OK responses, the same responses CSP values are captured from, so a canonicalising 308 (trailing slash, `http` → `https`) cannot raise a false alarm. Other required headers, including HSTS, are still checked on redirects.

### Added

- Workflow steps can name `waitForAlternatives`: further selector chains, written like `waitFor`, any one of which also satisfies the step. One workflow then covers an application that serves a step in more than one shape — a route behind a feature flag or experiment — instead of timing out whenever the other shape is served. Each chain is waited for on its own and the first with a visible match wins, so a hidden match of one never blocks a visible match of another; the step acts through the chain that matched. `waitFor` stays required; at most four alternatives, none empty.
- `collector-core` takes an optional **`lambda_reserved_concurrency`** for the ingest Lambda: the cap on simultaneous beacon processing, and so the per-hour bound on what a flood of forged beacons can cost downstream (every accepted observation is a DynamoDB write). Unreserved by default, so nothing changes for existing deployments or the examples — AWS requires 100 executions to stay unreserved in the Region across all functions' reservations, and fresh accounts ship with small quotas, so a default cap could fail the first apply. Because a throttled beacon is a lost observation, both alarm modules gain a throttle signal: `collector-core` alarms on any `Throttles` in a 5-minute window (`<prefix>-ingest-throttled`, gated by `create_alarms`) and `observability-datadog` mirrors it as a monitor (`monitor_ids.lambda_throttles`).
- `collector-core` takes an optional `permissions_boundary_arn` and attaches it to every IAM role it creates (the ingest Lambda role, the Firehose delivery role and the OIDC comparator role). Landing zones commonly let the Terraform deploy role create a role only when it carries a specific boundary, so without this seam the module could not be applied in such an estate at all; it defaults to none, so existing deployments and the examples are unchanged. A variable addition, so a minor version.
- An unanswered script request whose frame went away now says when, and which frame: the auditor report's `unansweredRequests` entries gain `detachedAtStep` and `detachedFrameUrl` (origin and path; schema 1.8.0), shown in the HTML report, the job summary and the run summary's **Script Requests Unanswered** list — e.g. `issued at step 9, frame detached at step 9 (https://challenge.example/widget)`. A request still outstanding when the browser context closes records the step it closed in. This tells a vendor frame replacing itself on its own schedule from a detach that coincided with one of the workflow's own actions. The exit code and the evidence-only disposition are unchanged.
- Trust through a vendor's frames: the transitive `initiatorHostMatcher` takes an optional `"kinds": ["document"]` (or `["script"]`, or both) to consider only those hops of the initiator chain. With `kinds: ["document"]` on a payment provider's hosts, an entry can identify and authorise the scripts the provider's own nested frames load (a card form, a wallet payframe, a captcha frame), which a load grant cannot reach. A document hop counts only when it is the frame the browser loaded the script into — chains alone can be forged by page code to reach a vendor frame's document, and the binding is what the page cannot forge. A synthetic-pass control: real-user observations never satisfy it. Without `kinds` the matcher behaves exactly as before; `--mode validate` rejects an empty or unknown `kinds`.
- Initiator chains on the real-user lane. The browser agent records who inserted each script, out to the page (up to 8 hops, inline inserters by a counter identity, never their content) and sends it as `initiatorChain` in a new **beacon schema version 2** (version 1 was never deployed and is no longer accepted). The comparator binds it, so the transitive `initiatorHostMatcher` works on real-user observations, `rum_*` alerts carry a **Loaded by** line, and an unidentified observation can be authorised by a granting ancestor that is identified and authorised on URL evidence alone. **Behaviour change:** an external real-user observation whose identifying entry authorises on URL evidence only (`nameMatcher`, `urlMatcher`, `hostMatcher`, `initiatorHostMatcher`, `targetTypeMatcher`, alone or composed) is now evaluated instead of merely recorded — a denial raises `rum_mismatched_script_detected` on the detection pass, and is recorded with the reason (not proposed as a candidate, which would sit behind the identifying entry) on the inventory pass. As on the synthetic lane, an inline observation never inherits and an observation a pending or declined entry identifies is never overridden by a grant. The agent ends every chain at the page as an `unknown` hop, never `document`. Entries that need a hash or content stay identification-only.
- Trust inherited through loaders. Every script now carries its **initiator chain** — who inserted it, who inserted that, out to the page (up to 8 hops, through inline scripts as well as external ones) — shown on every script row of the auditor report (`observed.initiatorChain`), in a _Loaded By_ column on unknown and mismatched script alerts, and on unanswered script requests. Two inventory shapes use it: `authorisesLoads: "direct" | "transitive"` (with optional `maxDepth` and a `loadsMatching` guard) on an authorised script entry authorises what that script loads, and `initiatorHostMatcher: { "host": …, "transitive": true, "maxDepth": … }` identifies a script by a host anywhere up its chain. Inheritance is fail-secure — an explicit verdict always wins (including an entry still pending review or declined), a granting script whose bytes no longer match poisons everything below it, a broken or missing chain inherits nothing, an inline script never grants and an inline load never inherits (both rest on evidence page code can forge), every grant must carry a `loadsMatching` guard that judges the loaded script on its own URL, content or hash, and `--mode validate` refuses a grant that is missing one, has one built only from run metadata (`workflowMatcher`/`targetTypeMatcher`) or `initiatorHostMatcher`, has one that admits `inline_script/` names, or sits on an unauthorised entry. Auditor report schema 1.7.0 adds `observed.initiatorChain`, `authorisation.inherited` and `inventoryEntry.provenance.grantedBy`.
- Payment page scoping: mark the workflow step that runs on the card-entry page with `paymentPage: true`, and the run alerts on and inventories only the payment page's SPA context — the browser document that page lives in, including anything an earlier client-side route loaded into it. Only earlier pages the payment page replaced — pages that never rendered a payment path, were never current at or after it, and were not a failed render that the monitor's own reload recovery replaced with an in-scope page — are recorded in the auditor report as `outside_payment` and never alerted on; the payment page, every page after it (a card-form reload, a 3-D Secure redirect, a confirmation page) and any failed render of the payment page stay in scope. Scope follows Chrome's own document boundary, so an application that drops the full page load before its payment page has the earlier scripts alerted on rather than hidden; anything that cannot be attributed stays in scope. Workflows without the marker behave exactly as before. Auditor report schema 1.4.0 adds `scope` to rows and `paymentScope` (page chain, payment-only counts, and `resolved: false` when a marked payment page could not be identified) to targets.
- Datadog observability option for the RUM collector: new `infra/observability-datadog` Terraform module mirroring the four CloudWatch alarm families plus the canary dead-man's switch as Datadog monitors (metrics flow CloudWatch → Datadog; the ingest path keeps zero vendor SDKs), and a `create_alarms` toggle on `collector-core` (default `true`) to disable the CloudWatch alarms when the monitors live in Datadog.
- Real-user script monitoring (feature 011): browser RUM agent with SRI-pinned release bundles, collector ingest Lambda (beacons and CSP violation reports), RUM comparison mode with dedicated alert categories, canary interlock, and Terraform modules for the collector stack.
- Release workflow publishing versioned artefacts on every `v*.*.*` tag: agent bundle with SHA-256 and SRI string, collector package with SHA-256, and a ready-to-paste inventory entry snippet.
