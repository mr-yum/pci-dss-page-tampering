# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Project Overview

This is a PCI DSS compliance system implementing **requirements 6.4.3 (Script Management)** and **11.6.1 (Detection and Alerting)** to prevent page tampering and e-skimming attacks on payment pages. The system provides:

### PCI DSS Compliance Goals

- **6.4.3 Script Management**: Maintain authorized inventory of all payment page scripts with justification and integrity verification
- **11.6.1 Detection and Alerting**: Continuous monitoring and alerting for unauthorized script/header modifications

### System Components

- **Inventory Service**: Updates baseline inventory of approved scripts and headers, alerts on new discoveries
- **Detection Service**: Monitors live applications against inventory, alerts on violations without modifying inventory
- **Dual Workflows**: Each target has both inventory and detection URLs for comprehensive coverage
- **Git-based Storage**: Inventories stored in separate Git repository for audit trail and version control

### Monitored Resources

- **External scripts** loaded from remote URLs with hash verification
- **Inline scripts** dynamically added during page execution
- **Security-impacting HTTP headers** (CSP, security headers)
- **Puppeteer workflows** simulating real user payment flows

## CLI Usage

The system is configured entirely via command-line parameters. No environment variables are used for execution configuration. (When running under GitHub Actions, the runner's standard `GITHUB_*` variables are read solely to annotate the auditor report with CI provenance and to append its job-summary digest — they never influence what the run does.) One deliberate carve-out: `--mode rum-compare` authenticates to AWS with ambient credentials/region from the environment (e.g. OIDC-assumed role in CI), never via CLI parameters — credentials do not belong on command lines.

### Basic Syntax

```bash
npm start -- [OPTIONS]
```

### Required Parameters

| Parameter             | Description                                                            | Example                            |
| --------------------- | ---------------------------------------------------------------------- | ---------------------------------- |
| `--repo <url>`        | Inventory repository URL (HTTPS or file://)                            | `https://github.com/org/inventory` |
| `--git-token <token>` | Git authentication token (required for HTTPS; optional for `validate`) | `${{ secrets.GITHUB_TOKEN }}`      |

### Optional Parameters

| Parameter                   | Description                                                                                                      | Default             |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- | ------------------- |
| `--mode <mode>`             | Execution mode: `inventory`, `detection`, `all`, `validate`, or `rum-compare`                                    | `all`               |
| `--target <name>`           | Process specific target (e.g., "1.0")                                                                            | all targets         |
| `--slack-token <token>`     | Slack token for alerts (logs to console if omitted)                                                              | -                   |
| `--inventory-branch <name>` | Branch for inventory operations                                                                                  | `inventory-updates` |
| `--detection-branch <name>` | Branch for detection operations                                                                                  | `main`              |
| `--totp-seed <name>=<seed>` | Named base32 TOTP seed for `totp` workflow steps (repeatable)                                                    | -                   |
| `--rum-queue-url <url>`     | SQS queue URL (or `file://` dir for local testing) of novel RUM observations; required with `--mode rum-compare` | -                   |
| `--report-dir <path>`       | Directory for auditor report artefacts (HTML + JSON)                                                             | - (no report)       |
| `--help`                    | Display help message and exit                                                                                    | -                   |

### Usage Examples

```bash
# Run full workflow (inventory + detection) for all targets
npm start -- --repo https://github.com/org/inventory --git-token $TOKEN

# Run inventory only for a specific target
npm start -- --mode inventory --target 1.0 --repo https://github.com/org/inventory --git-token $TOKEN

# Run detection with Slack alerts
npm start -- --mode detection --repo https://github.com/org/inventory --git-token $TOKEN --slack-token $SLACK_TOKEN

# Run detection with custom branches
npm start -- --mode detection --detection-branch release/v2.0 --repo https://github.com/org/inventory --git-token $TOKEN

# Compare queued real-user observations against the inventory
npm start -- --mode rum-compare --repo https://github.com/org/inventory --git-token $TOKEN --rum-queue-url https://sqs.ap-southeast-2.amazonaws.com/123456789012/rum-novel-observations --slack-token $SLACK_TOKEN

# Local testing with file protocol (no authentication needed)
npm start -- --repo file:///path/to/local/inventory --git-token dummy

# CI validation of the inventory repo (no token needed for file://)
npm start -- --mode validate --repo file://$PWD --inventory-branch $GITHUB_HEAD_REF
```

### Exit Codes

| Code | Meaning                                                                                                                                                                                                                                           |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0    | Success (including --help)                                                                                                                                                                                                                        |
| 1    | Validation error (invalid arguments)                                                                                                                                                                                                              |
| 2    | Execution error (Git, network, workflow failure) — including a run in which one or more targets failed while the rest completed, in which a script on the payment page could not be read, or in which an alert could not be delivered (see below) |

### Partial runs

A target whose workflow fails (timeout, missing element, backend error) does **not** abort the run. The remaining variations in that pass still execute, the inventory diff and push still happen for the observations that were made (the diff is additive, so a partial observation set is safe), and under `--mode all` the detection pass still runs. The failure is recorded in the auditor report (`run.status: "partial"`) and named in the end-of-run Slack summary, whose headline switches from :white_check_mark: to :warning: (some targets failed) or :red_circle: (every target failed) and lists each failed target with its pass and reason under _Targets Failed_. The process then exits 2 so CI stays red — a run with an unmonitored payment page must never look green. The same accounting covers **alerts that were produced but not delivered**: Slack answers a rejected payload with HTTP 200 and `ok: false`, `SlackAlertService` records every such failure (`getDeliveryFailures()`), the summary lists them under _Alerts Not Delivered_ with the alert kind, target and reason, and the run exits 2 for them too — a finding nobody was told about is an unmonitored finding. The same accounting covers **scripts that arrived but could not be read**: a script response whose body the monitor could not read is never hashed or compared, so it is recorded (URL, resource type, status, reason, the top-level document it belonged to and the workflow step in progress — `UnreadScriptResponse`, `src/types/script.ts`), split by payment scope like every other observation (unattributed stays in), listed in the auditor report under each target's `unreadScripts` and named in the summary under _Scripts Not Read_. One in payment scope — on either pass — marks the run `partial`, switches the headline to :warning: and exits 2 exactly like a failed target, because a payment page with a script nobody examined was not monitored; one on an earlier page the payment page replaced is listed for evidence (_Scripts Not Read Outside The Payment Page_) and leaves the exit code alone. A script **request that never got a response** is not an unread script and never fails the run, in either scope: in the observed Chrome behaviour (probe, 2026-10-02) Puppeteer surfaces a script's response only once its body is complete, and a classic script cannot execute before then, so a request still unanswered when the context closes never ran on the page — there is nothing unmonitored. It is recorded as evidence instead (`UnansweredScriptRequest`; the report's `unansweredRequests`, summary _Script Requests Unanswered_), because the request itself deserves a human's eye — a URL the page built wrongly appears nowhere else. The record names the step that **issued** the request (`step`), and — when its frame went away with the request outstanding — the step running **at the detach** and the frame's URL (`detachedAtStep`, `detachedFrameUrl`, redacted to origin + path where shown; schema 1.8.0), rendered `issued at step 9, frame detached at step 9 (https://challenge.example/widget)`. A request cut off by the context closing records the step it closed in (the last step) through the close-grace settle, so that case reads the same way. The two steps are what separate the usual source of these rows — a vendor frame replacing itself mid-load on its own schedule (a captcha widget re-creating its iframe, a card provider's frame tearing down) — from a detach that coincided with one of the monitor's own actions, which is the one worth a look. The detach step comes from the `framedetached` listener's `currentStep`, never the request's own: `PendingScriptReads.frameDetached` called without a step records neither field. That inference is an observation, not a guarantee, so the evidence-only disposition rests on backstops that turn a request into an unread script instead: Puppeteer's `requestfinished` with no response surfaced (crbug.com/883475 — Puppeteer emits it regardless), Chrome's own `Network.loadingFinished` seen on the monitor's sessions, and any response that lands after the seal — which stays accounted for as a pending read until that read settles, so a read Puppeteer never settles (it does not reject one whose session disconnects) is still returned by the close-grace settle as unread. A late non-script answer (a 404, a 502) leaves the request listed with the answer noted, and is never turned into an unread script by a finished body under its request id (that body is the error page's); a late 3xx takes a request off the list, since the request it redirects to is tracked on its own and shares the hop's request id. Three lists in the run summary are capped — _Scripts Not Read_, _Scripts Not Read Outside The Payment Page_ and _Script Requests Unanswered_ — because a widespread outage can fill them with hundreds of entries and Slack rejects a message over 50 blocks wholesale, which would fail the run while telling nobody anything. The cap is on rows, never on targets: each list gives at most 20 rows — the first to each affected target in turn — names any further targets in compact "Also affected" lines of target names alone, then says how many entries were not shown and points at the auditor report and the run log (`namedListSections`), so the rule below still holds: every target with an unmonitored page is named. _Targets Failed_ and _Alerts Not Delivered_ are never truncated. This accounting belongs to the synthetic inventory/detection passes; `--mode rum-compare` counts delivery failures in its own drain summary and keeps exit 0 by design (alert failures never block queue routing). Only run-level failures (inventory pull, push, PR creation, browser launch) abort the run outright. The rule for a notification design: the per-finding alerts speak only for targets that were observed, so the summary is the one place a reader learns which page went unmonitored, and it must name them rather than count them.

### Execution Modes

- **`inventory`**: Updates baseline inventory, pushes changes to Git
- **`detection`**: Read-only comparison against inventory, sends alerts
- **`all`**: Runs inventory first, then detection (default)
- **`validate`**: Runs full deserialization (Zod schema + `createMatcher()` + workflow file resolution) against the inventory repo and exits. No Puppeteer, no alerting, no push. Use as a CI pre-merge check in the script-inventory repository.
- **`rum-compare`**: Drains first-sighting observations reported from real user sessions and evaluates them against the inventory with the same matcher pipeline: detection-pass observations raise `rum_*` alerts; inventory-pass observations feed the candidate PR flow. Read-only except for candidate PRs; hourly scheduling lives in the inventory repository. Requires `--rum-queue-url`.

For detailed implementation documentation, see `specs/008-refactor-the-code/quickstart.md`.

## Architecture

### Core Services

1. **DetectionService** (`src/services/detection.ts`) - Main orchestrator that:
   - Launches Puppeteer browser sessions (isolated context per target run; the `HeadlessChrome` UA token is normalised to `Chrome` so the monitor sees what real users are served — bot mitigation blocks on the headless token, and cloaking attackers key on it)
   - Asks Chrome to keep response bodies outside the renderer (`Network.configureDurableMessages`) before the first navigation — on the page (`retainResponseBodies`) and on every out-of-process iframe's own session (`frameBodyRetention`) — and waits for in-flight script requests and body reads (`PendingScriptReads`, `src/handlers/script.ts`) before closing the context. Everything outstanding at that deadline ends in one of three places: a body still being read, or a request whose body finished although no response was surfaced (Puppeteer's `requestfinished` with a null response, or Chrome's raw `Network.loadingFinished` on the monitor's own sessions), is recorded as **unread** and fails the run; a request with no response and no sign its body finished is recorded as **evidence** only (`unansweredRequests`); and a late non-OK answer leaves it in the evidence list with its status, while a late 3xx hands it to the request it redirects to. A frame's requests stop holding the deadline once the frame detaches. The run is then sealed so a body that lands late is recorded as unread rather than compared. See _Unread script bodies_ below for why each exists
   - Executes workflow steps defined in `src/workflows/`
   - Captures scripts and headers during page navigation
   - Returns detection summaries for comparison

2. **ComparisonServices** - Compare detected resources against inventory using matcher pipeline:
   - `ScriptComparisonService` (`src/services/comparison/script.ts`) - Uses modular matcher system for flexible script identification and authorization
   - `HeaderComparisonService` (`src/services/comparison/header.ts`) - Uses matcher system for header identification (case-insensitive names) and authorization (case-sensitive values)

3. **InventoryService** (`src/services/inventory.ts`) - Manages resource inventories stored in Git:
   - Processes typed comparison results (ComparisonResultType[]) directly for inventory updates
   - Generic update handler for both scripts and headers using discriminated union switch
   - Single-pass processing eliminating legacy type conversions
   - Idempotent updates prevent duplicate hashes/matchers; pending entries (`authorised: false`) already covering a script are never re-appended on later runs
   - New scripts are identified by exact name (URL / inline id) — except inline scripts carrying the shared `inline_script/id_not_found` fallback, which get a provenance-based matcher instead: `andMatcher` of the initiator host (`hostMatcher`) and an anchored 64-char content snippet (`contentMatcher`, both ends anchored when the whole body fits the window). Two exceptions: content-only matching when the initiator URL is missing/unparseable, and the exact-name matcher (degenerate) for whitespace-only content — never a universal matcher
   - Array syntax conversion preserves original authorization metadata

4. **AlertService** (`src/services/alert/slack.ts`) - Sends Slack notifications for detected changes, plus the end-of-run summary (`alertOnRunCompletion`) that names the targets that succeeded, the ones that failed, the scripts that could not be read (with target, pass, step and page), the script requests that were never answered (evidence only — they leave the headline alone), and the alerts that could not be delivered. Table-based alerts are fitted to Slack's 10,000-character table budget before sending (`boundedTable`): cells are clipped, rows are kept in order until the budget is spent, and a trailing note says how many were cut and points at the auditor report — an unbounded table is rejected wholesale as `invalid_blocks`, which is how a 14-row CSP mismatch alert once vanished without trace

5. **ReportService** (`src/services/report/`) - Produces the auditor report when `--report-dir` is set:
   - `ReportCollector` is fed once per target run from `main.ts`, after both comparisons and _before_ the inventory diff, so the report records the baseline the comparison actually ran against
   - Deliberately **not** an `IAlertService`: alerting is called twice per target with a partial view, fires after the diff, and drops `authorized_*` results — the very rows a census needs
   - Results are mapped to rows eagerly so the heavy comparison results (full script bodies, `Target`, matcher trees) can be freed
   - Emitted per pass from a `finally`, so a partially-failed run still produces evidence for the targets that succeeded; a write failure is logged and never fails the run
   - Script responses whose body could not be read are not census rows (there is no content to hash or judge) but a per-target `unreadScripts` list, scoped like rows. In payment scope they make `run.status` `partial` and count in `summary.scriptsUnread` (schema 1.5.0), so a census missing a payment-page script never reads as complete. Script requests with no response and no sign their body finished are a separate per-target `unansweredRequests` list (schema 1.6.0, counted in every scope in `summary.requestsUnanswered`, a late non-OK answer noted in the reason) and never make the run partial; one whose body finished although no response was surfaced is an `unreadScripts` row with `status: 0` and does
   - When a target's workflow marks a payment page, the target gets `paymentScope` (the redacted page chain, each document with its scope, the payment document marked). If the payment page was identified, the run is recorded in two calls (`scope: 'payment'` and `scope: 'outside_payment'`, built by `reportRecordsFor`), rows carry `scope`, and `paymentScope.counts` covers the payment rows alone while `counts` stays the full census. If it was not identified, there is one call, rows carry no `scope`, everything was alerted on, and `paymentScope.resolved` is `false` with `counts` equal to the census — recorded so a marker that stopped resolving is visible rather than looking unmarked. A resource observed in both scopes yields two rows: the payment row keeps its natural `rowId`, the outside row gets a derived one. The step summary never lists `outside_payment` rows as findings
   - `--mode all` writes two documents (one per pass) joined by `run.correlationId`
   - Every authorised row carries `file:line` + JSON pointer provenance for the matcher that authorised it, resolved by `src/utils/provenance.ts` from the raw inventory text retained on `Inventory.source`. An inherited row (`authorisation.inherited`, schema 1.7.0) cites the granting entry and its `authorisesLoads` line (`grantedBy`) with `authorisedBy: null` — replaying the granting entry's matcher against the inherited script would disagree, and a node that did not run must never be named
   - That same retained text is copied verbatim into `<report-dir>/<pass>/inventory/targets/*.json` and digested in `run.inventorySources`, so the cited line numbers stay resolvable after the branch moves. Per pass, not shared: under `--mode all` the passes read different branches
   - The Slack success notification links the **workflow run page**, not the artifact: the artifact uploads in a later workflow step and has no URL while the tool is still running. The run page lists it and renders the job-summary digest. Outside CI the written paths are shown instead (`ExecutionSummary.auditorReport`)

### RUM surveillance (`--mode rum-compare`)

A second observation lane, independent of Puppeteer. The synthetic passes walk one scripted checkout per target; real users walk everything else — every route, every experiment arm, every error path — so this lane watches live sessions and feeds their findings into the same matcher pipeline. Four components joined by one wire contract:

1. **Browser agent** (`agent/`) - a dependency-free IIFE (`npm run build:agent` → `dist/agent/agent.js`, SRI printed) embedded **site-wide, not just on the payment page**: an injection that lands two soft navigations before checkout still belongs to the session that reaches it (FR-001). Attribution dictates its shape. `Node.prototype.appendChild`/`insertBefore` are patched (call through first, then observe) because at insertion time `document.currentScript` still names the inserting script, while inside a MutationObserver callback — a microtask running after the inserter finished — it is already null, so a pure-observer design cannot attribute at all. The MutationObserver (childList+subtree) and a buffered `PerformanceObserver` (`type: 'resource'`) are safety nets for what the patch cannot see (parser-inserted markup, `innerHTML`, fetches predating the agent); they capture unattributed and fall back to the document URL. A document-level `securitypolicyviolation` listener captures CSP violations. Observer callbacks only enqueue (`agent/src/capture.ts`); slicing, SHA-256 and dedupe are deferred to `requestIdleCallback` slots (`agent/src/fingerprint.ts`) — which is why an inline script travels as `{length, head, tail}` with 128-char **strict** prefix/suffix windows, and is not hashed at all above a 512 KB UTF-8 ceiling (`oversize: true` instead): a multi-megabyte bundle must never cost main-thread time on a payment page. Transmission is `navigator.sendBeacon` with a `text/plain` Blob (CORS-safelisted, so no preflight, and it survives page-hide), keepalive `fetch` as fallback, split into beacons of ≤ 24 observations / ≤ 32 KB. Each flush cycle appends exactly one agent-health observation carrying the agent's own p95 task time and drop count, so the monitor's overhead is measured rather than asserted. The insertion patch also records each inserted script's **initiator chain** (beacon v2, `initiatorChain`): `[the inserter's hop, ...the inserter's own recorded chain]`, capped at 8 hops — an external inserter by its URL, an inline one by a per-element counter identity `inline_script/rum#<n>` (never its content), and the page itself — reached when the inserter is one the patch never saw inserted (markup, or an unpatched insertion path) or when there is no `currentScript` at all — as an **`unknown`** hop, origin + path only. The agent never emits a `document` hop (the schema accepts the shared hop type), so on this lane the page is never a known hop: test with that shape. Safety-net captures (MutationObserver, PerformanceObserver) carry no chain. Configuration is one attribute — `data-collector` on the agent's own script tag (`agent/src/agent.ts`); without it the agent stays inert. The bundle imports the beacon schema with `import type` only, so Zod never reaches the page
2. **Collector** (`collector/`) - an ingest Lambda behind a Function URL (`collector/src/ingest.ts`, `npm run build:collector` → `dist/collector/ingest.zip`). The ordering is the security property: the edge shared secret is verified with a constant-time compare **before the body is read**, so an unauthenticated request never buys a parse; then the `Origin` header is matched against the configured `ORIGIN_TARGETS` map, and that mapping is the **sole authority** on which target and which pass (`inventory` / `detection`) an observation belongs to — a page cannot nominate its own target. Every path returns **204 with an empty body**, auth failure and unmapped origin and schema rejection alike: a public endpoint must not be an oracle for what it accepts. Accepted beacons are archived **verbatim** to Firehose (stamped with target and receipt time, never rewritten) so the archive stays admissible evidence; each observation is then keyed for novelty in DynamoDB as `target#identity#initiatorHost` with a 90-day TTL — **one write per observation**, an `UpdateItem` upsert whose returned prior state answers novel-or-repeat — a prior record whose `ttl` has passed counts as none, because DynamoDB deletes expired items lazily and the upsert has just refreshed that `ttl`; it is reset to the new sighting with a conditional write so concurrent returns yield one first sighting (it replaced a conditional `PutItem` plus a counter `UpdateItem`: a failed conditional write is still billed, so every repeat, the common case, cost two writes for one fact). The compensating delete on an SQS failure needs `dynamodb:DeleteItem` on the Lambda role; the module's policy lacked it until 2026-10, and because the compensation is best-effort behind the always-204 contract the `AccessDenied` surfaced only in logs while the pk went on suppressing re-enqueue for its TTL — a best-effort step whose failure is swallowed needs a test that its permission exists (`infra/tests/collector_core.tftest.hcl`). The SPA route is deliberately excluded from the key (a known script on a new route is not a new script) and the initiator host is deliberately included (a known script injected by a new origin is a supply-chain signal). Only **first sightings** reach SQS — repeat observations bump `last_seen`/`sessions` and stop there, which is what keeps a million sessions a day from becoming a million comparator messages. A second route, `POST /csp-reports`, accepts browser-native `report-uri` and Reporting API `report-to` payloads and maps them to synthetic `csp-violation` observations through the identical archive → novelty → enqueue pipeline
3. **Comparator** (`--mode rum-compare`, `src/rum/`) - drain → normalise → route. `drain.ts` reads through a queue adapter (`https://` SQS, or a `file://` directory for local development) under a strict delete discipline: a message is deleted only once routing succeeded, a schema-invalid body is dead-lettered without ever reaching the handler, and a handler throw leaves it for redelivery. `normalise.ts` binds an observation to a `Matchable` **without inventing content**: an external script gets `name`/`url` and `identificationOnly` (its body is opaque to a browser observer, so authorisation is attempted only on URL evidence — see below), an inline script gets the client-computed hash plus _either_ full `content` (when the whole source fits one 128-char window) _or_ `contentEvidence` (`{length, head, tail}`) — never a `head…tail` reconstruction. That is what evidence-aware authorisation rests on: the same inventory entries judge RUM and synthetic observations, but each matcher decides on the evidence it actually holds, a window match authorises, and a window non-match fails secure because a match beyond the excerpt cannot be ruled out (see the Matcher System notes below). `route.ts` splits on the pass the collector stamped. The **detection lane** alerts — `rum_uninventoried_script_detected`, `rum_mismatched_script_detected`, `rum_csp_violation_reported` — each carrying prevalence (`first_seen`), the SPA route at first sighting, and the `inventoryRef` commit SHA the observation was judged against, so an alert states which baseline it disagreed with. CSP is **opt-in only**: it fires solely when `alerts.rum.cspViolationReported` is configured, with no fallback destination, because real-user CSP reports carry heavy browser-extension noise and a fallback would switch the category on for every existing inventory. The **inventory lane** never alerts and never authorises: unidentified observations become pending candidates (`authorised: false`) fed to the existing `InventoryService.diff` → push → PR flow. An inline observation that is identified but _unauthorised_ also becomes a candidate rather than a hash append — appending a hash to an authorised entry is de-facto authorisation, and a client-reported hash must never buy that. **URL evidence** (`src/rum/url-evidence.ts`): an external observation stays identification-only unless the identifying entry's authoriser consumes only evidence a URL-only observation carries — every leaf `name`/`url`/`host`/`initiator-host`/`targetType`, except an `initiatorHostMatcher` limited to `document` hops, which no beacon can satisfy (`consumesOnlyUrlEvidence`; one hash, content or workflow leaf anywhere makes the whole authoriser unevaluable, so an OR alternative that would have passed on a hash is never read as a denial). Such an entry is evaluated exactly: authorised → recorded, denied → `rum_mismatched_script_detected` on the detection lane and recorded with the reason (never proposed) on the inventory lane. **Inheritance** (`inheritOnUrlEvidence`): an **external** observation that **no** entry identifies — pending and declined entries included, as on the synthetic lane — walks its agent-reported chain (an inline observation never inherits); ancestors are not in the batch (novelty dedupe never re-reports a known loader), so each ancestor hop is judged from the hop alone as a URL-only observation — it must be identified and authorised on URL evidence, an inline hop (no evidence) or a `document`/`unknown` hop ends the walk, and the first ancestor whose grant covers the depth and whose mandatory `loadsMatching` accepts the observation vouches for it (recorded on both lanes). Every rule has a test in `src/rum/initiator-chain.test.ts`, each checked by breaking it. The chain rides `rum_*` alert context as a **Loaded by** line (redacted). The beacon is page-controlled: code on the page can claim any chain (one line redefining `document.currentScript` does it), as it can already claim any URL. What keeps a forged chain from vouching for a skimmer is the grant's `loadsMatching` guard, judged on the observation's **own** evidence only (`ownEvidence`): the external script's own URL — never its `initiator` or chain, which are who claims to have inserted it; inline loads never reach a guard on either lane. Two more limits: an `initiatorHostMatcher` authoriser is judged only when the chain's first hop is real (the agent's `initiator` is the page URL whenever no script was executing), and the novelty key carries only the immediate initiator host, so a verdict that depends on deeper hops is made once, on the first sighting, for the key's 90-day life. On the inventory lane a URL-evidence denial is recorded, not proposed: a new exact-name candidate would sit behind the entry that identified it (first match wins) and never apply. Inserting an inline script runs it inside `appendChild`, so the agent records an element's chain **before** calling through — `test/integration/rum-agent-chain.test.ts` bundles the real agent into real Chrome to prove it, which jsdom (no script execution) cannot
4. **Infrastructure** (`infra/`) - four Terraform modules: `collector-core` (Lambda + Function URL, Firehose → KMS-encrypted S3 archive, DynamoDB novelty table, SQS queue + DLQ, alarms, and the GitHub OIDC role the comparator assumes) plus `edge-cloudfront` and `edge-cloudflare`. Both edges authenticate to the origin by injecting an `x-collector-edge-key` shared secret rather than signing requests, for one hard reason: OAC/SigV4 signing of a POST requires the **client** to send `x-amz-content-sha256`, and `navigator.sendBeacon` cannot set headers — under OAC every beacon would be rejected at the Function URL. The collector runs with **no VPC** (no NAT, no ENI cold-start tax, nothing to misconfigure); the contract is enforced by `infra/tests/no-vpc-check.sh`, a source-level grep, because `terraform test` cannot assert the absence of a resource type across a plan. Alarms cover queue age (comparator drain stalled), ingest error rate and DLQ depth — and, the one that matters for 11.6.1, a **per-target beacon-volume anomaly alarm with missing data treated as breaching**, so an attacker who strips the agent to silence the monitor trips the alarm by the silence itself. The fourth module, `observability-datadog`, mirrors those alarm semantics as Datadog monitors for estates whose on-call watches Datadog (deployed beside core with `create_alarms = false`): emission stays CloudWatch — the ingest path keeps zero vendor SDKs and no runtime keys — and metrics flow CloudWatch → Datadog via the AWS integration, with Metric Streams as the documented prerequisite for the silence-sensitive monitors

The **beacon schema** (`src/types/beacon.ts`) is the three-way contract between producer (agent), validator (collector) and consumer (comparator), with fixtures in `test/fixtures/beacons/` imported by all three test suites so a breaking change fails at the seam rather than in production. Every string field is individually length-capped (URLs 2048, route 512, fingerprint windows 128, initiator chains 8 hops of a capped URL or an inline_script/rum counter identity, whole beacon 32 KB), which makes the schema _structurally_ incapable of carrying page content, cookies, form values or customer identifiers — the privacy guarantee is a shape, not a policy. Changes to it require security review.

### Data Flow

1. **Inventory Workflow**:
   - Executes against staging/inventory targets
   - Comparison services return typed results (ComparisonResultType[])
   - InventoryService processes results directly in single pass
   - Updates baseline inventory with newly discovered scripts/headers
   - Alerts on unidentified resources (requires manual authorization)
   - Pushes changes to Git repository
   - Opens a pull request from `--inventory-branch` into `--detection-branch`
     (GitHub HTTPS repos only) so the inventory repo's `--mode validate` CI
     check runs and humans can review. PR creation failure fails the run;
     the `--git-token` must have `pull_requests: write` permission.

2. **Detection Workflow**:
   - Executes against production/detection targets
   - Comparison services return typed results (ComparisonResultType[])
   - Compares findings against existing inventory (read-only)
   - Alerts on uninventoried or hash-mismatched resources
   - No inventory modifications

3. **Script Comparison Flow** (Matcher Pipeline):
   - **Identification**: Iterate inventory entries in order, skipping entries whose `authorisationInfo.authorised` is not `true` (pending/declined), and test `identifyWith` matcher against detected script
   - **First-Match-Wins**: Return first inventory entry where `identifyWith.identify()` returns true
   - **Authorization**: If identified, test `authoriseWith.matcher` against script content; the entry's own `authorised` flag gates the verdict too (as for headers), and every matcher denies when its own `authorisationInfo.authorised` is `false`
   - **Result**: Return typed comparison result (UnknownScriptFound, KnownScriptWithUnauthorisedContentFound, or AuthorizedScriptFound)
   - **Fail-Secure**: Null/empty content triggers UnknownScriptFound (cannot be safely matched)
   - **Pass 2 — inheritance** (`inheritAuthorisation`, see _Transitive trust_): every **external** script still `unknown` that **no** entry identifies — pending and declined entries included — walks its initiator chain outward and becomes `AuthorizedScriptFound` with `inherited` set at the first hop whose every observation is an external script pass 1 explicitly authorised under an entry granting `authorisesLoads` at that depth, provided the grant's `loadsMatching` guard identifies the script on its own evidence; every hop crossed on the way must itself be authorised. Inline loads never inherit, inline scripts never grant, and nothing else changes verdict
   - **Metadata Access**: Authorization metadata available via `authoriseWith.authorisationInfo` for alert context

4. **Alert Categories**:
   - `new_inventory_script_identified`: New script found during inventory (needs authorization)
   - `uninventoried_script_detected`: Unknown script found during detection
   - `mismatched_script_detected`: Known script with changed hash (potential tampering)

#### Authorization Structure (Enhanced 2025-10)

Each inventory entry (scripts and headers) uses a nested authorization structure:

- `identifyWith`: Matcher for identifying the resource (NameMatcher/HeaderNameMatcher/ContentMatcher/HashMatcher/HostMatcher/UrlMatcher/WorkflowMatcher/TargetTypeMatcher/CspDirectiveMatcher/OrMatcher/AndMatcher)
- `authoriseWith`: Matcher configuration with authorization metadata:
  - Can be a single matcher (NameMatcher, ContentMatcher, HashMatcher, HostMatcher, UrlMatcher, CspDirectiveMatcher, OrMatcher, AndMatcher)
  - Can be an array of matchers (syntactic sugar for OrMatcher)
  - Must include `authorisationInfo` with description, authorization status, and date
  - Composite matchers (OrMatcher, AndMatcher) can have nested `authorisationInfo` at each level

**Simple Matcher Example**:

```json
{
  "identifyWith": { "nameMatcher": "^https://example\\.com/script\\.js$" },
  "authoriseWith": {
    "hashes": [{ "timestamp": "2025-10-21T12:00:00.000Z", "hash": { "value": "abc123..." } }],
    "authorisationInfo": {
      "description": "Analytics script for conversion tracking",
      "authorised": true,
      "date": "2025-10-21T12:00:00.000Z"
    }
  }
}
```

**Composite Matcher Example (AND logic for CSP)**:

```json
{
  "identifyWith": { "headerNameMatcher": "^content-security-policy$" },
  "authoriseWith": {
    "andMatcher": [{ "contentMatcher": "default-src\\s+https:" }, { "contentMatcher": "script-src\\s+https:" }, { "contentMatcher": "object-src\\s+'none'" }],
    "authorisationInfo": {
      "description": "CSP requiring all three critical directives",
      "authorised": true,
      "date": "2025-10-24T12:00:00.000Z"
    }
  }
}
```

**Array Syntax Example (OR logic for multiple versions)**:

```json
{
  "identifyWith": { "nameMatcher": "^https://cdn\\.example\\.com/analytics\\.js$" },
  "authoriseWith": [
    {
      "hashes": [{ "timestamp": "2025-10-01T00:00:00.000Z", "hash": { "value": "abc123..." } }],
      "authorisationInfo": { "description": "Version 1.0.0", "authorised": true, "date": "2025-10-01T00:00:00.000Z" }
    },
    {
      "hashes": [{ "timestamp": "2025-10-15T00:00:00.000Z", "hash": { "value": "def456..." } }],
      "authorisationInfo": { "description": "Version 1.1.0", "authorised": true, "date": "2025-10-15T00:00:00.000Z" }
    }
  ]
}
```

This structure ensures authorization logic (matcher) and metadata are cohesively linked.

#### Matcher System (Refactored 2025-10)

- **Matcher Interface** (`src/types/matcher/matcher.interface.ts`) - Strategy pattern for script and header matching with `identify()` and `authorize()` methods. Every `Matchable` field carries what its name says, for every resource type: `name` is the script URL / inline id / header name; `content` is the actual content (external script response body, inline script source, or header value — never the URL as a stand-in); optional `hash` is the SHA-256 of that content; optional `url` is the single source of truth for provenance, populated for response headers (URL of the emitting response), external scripts (the script's own URL), and inline scripts (initiator URL captured at insertion time by the page-attribution shim, falling back to `location.href` for parser-inserted scripts); optional `workflowId` is the stable checkout-variation identifier assigned by orchestration; optional `initiator` / `initiatorChain` say who loaded a script (see _Transitive trust_); optional `frameUrl` is the frame the browser loaded an external script into (synthetic lane only — browser evidence, used to bind `document` hops).
- **NameMatcher** (`src/types/matcher/name-matcher.ts`) - Matches scripts by URL using regex patterns (case-sensitive, for external scripts with dynamic parameters)
- **HeaderNameMatcher** (`src/types/matcher/header-name-matcher.ts`) - Matches headers by name using regex patterns (case-insensitive per RFC 7230, for HTTP header identification)
- **ContentMatcher** (`src/types/matcher/content-matcher.ts`) - Matches by content using regex patterns (case-sensitive, against actual content: external script bodies, inline script source, or header values — never the URL; use NameMatcher/UrlMatcher/HostMatcher for URL-based matching). Evidence-aware for real-user (RUM) inline observations whose full source never travels: a source that fits one 128-char fingerprint window evaluates as full content, while longer sources carry strict-prefix/suffix head/tail windows (`Matchable.contentEvidence`) against which only soundly evaluable patterns decide — a `^`-anchored pattern (no bare `$`) matching the head, or a `$`-anchored one (no bare `^`) matching the tail, is a sound accept; an anchored window non-match or an unanchored/whole-content pattern fails secure with an explicit bounded-excerpt reason (a match beyond the excerpt can never be ruled out)
- **HashMatcher** (`src/types/matcher/hash-matcher.ts`) - Matches scripts by SHA-256 hash (scripts only, for strict integrity verification). Its fail-secure gate is the **hash's** presence, not the content's: a missing or empty `Matchable.hash` denies with `hash is missing`, while null content is not pre-checked at all. Synthetic detections always carry both (and `compare()` pre-gates null content before any matcher runs), but a real-user inline observation legitimately arrives with a client-computed hash and no content, and gating on content would have made every such observation unauthorisable. Hash identification works, but inventory entries should normally identify by stable name/content/provenance and use hashes for authorization; otherwise changed bytes are classified as an unknown script instead of known unauthorized content.
- **HostMatcher** (`src/types/matcher/host-matcher.ts`) - Derives the host portion of `Matchable.url` on the fly and regex-matches against it. Use when the inventory cares about origin but not path (e.g. "any CSP from `*.checkout.example`"). Fails-secure when `url` is missing or unparseable.
- **UrlMatcher** (`src/types/matcher/url-matcher.ts`) - Regex-matches the full `Matchable.url` (host + path + query). Use when path precision matters (e.g. _"only `https://payments.example.com/sdk/client-v1.js`, not arbitrary paths"_). Fails-secure when `url` is missing.
- **InitiatorHostMatcher** (`src/types/matcher/initiator-host-matcher.ts`) - Derives the host of `Matchable.initiator` — the URL of whatever inserted or loaded the script — and regex-matches against it, so an entry can constrain WHO may load a script independently of the script's own URL: `andMatcher: [{ nameMatcher: "^https://cdn\\.example\\.net/sdk\\.js$" }, { initiatorHostMatcher: "^pay\\.example\\.com$" }]` alerts the moment the allow-listed SDK arrives via any other host. This is how the RUM novelty key's initiator dimension becomes an alert: the key re-queues a known script re-injected by a new source, and the inventory entry — never the collector — decides whether that matters, as loose or tight as the author wants. Evidence: RUM external and inline observations carry the initiator; synthetic inline scripts carry it from the page-attribution shim; synthetic external scripts carry it from the CDP request initiator (script-stack top frame **below the shim's own wrapper frame**, else the initiator/document URL — the same immediate-inserter semantics as the agent's `document.currentScript` capture; see _Transitive trust_ for why the shim frame has to be removed). Fails secure when the initiator is missing or unparseable; headers never carry one, so it can never identify a header. **Transitive form**: `{ "initiatorHostMatcher": { "host": "<regex>", "transitive": true, "maxDepth": 8 } }` matches the host of **any** hop of `Matchable.initiatorChain` (and of any forked path) within `maxDepth` (1–8, default 8); it denies `initiator chain is missing` on a missing/empty chain, evaluates a chain ending in an `unknown` hop over its known prefix only, skips inline hops (no host), and names the chain in a denial (`loaded by a.example ← b.example ← page c.example`). `transitive` must be literally `true` in the object form, so the object form can never silently mean the immediate-hop form; the string form is unchanged. **Hop kinds**: an optional `"kinds": ["document"]` / `["script"]` / both (non-empty; duplicates tolerated, serialised canonically) limits the hops considered — a `script` hop never satisfies `["document"]` nor a `document` hop `["script"]` — and, with `kinds` given, a `document` hop counts only when **bound**: same origin as `Matchable.frameUrl`, the frame Chrome reports the script's own request was issued from. Without `kinds` the object form is exactly as before (every hop, unbound). The denial names the kinds and the script's frame host; `getDescription()` reads `initiator-host(transitive, ≤8 hops, document hops):/…/`. See _Transitive trust_ for why the binding exists.
- **WorkflowMatcher** (`src/types/matcher/workflow-matcher.ts`) - Regex-matches `Matchable.workflowId` so a shared inventory entry can apply to one or more checkout variations. Fails secure when `workflowId` is missing or empty.
- **TargetTypeMatcher** (`src/types/matcher/target-type-matcher.ts`) - Regex-matches `Matchable.targetType` (`inventory` or `detection`), scoping an entry to one pass. `workflowMatcher` cannot do this: a workflow id names a checkout variation, and one variation owns both an inventory and a detection target, so it is live during both passes. Use it — normally inside an `andMatcher` — to authorise a staging-only origin without also trusting it on the production payment page, e.g. `andMatcher: [{ targetTypeMatcher: "^inventory$" }, { nameMatcher: "^https://sandbox\\.provider\\.example/.+$" }]`. Fails secure when the target type is missing or empty.
- **CspDirectiveMatcher** (`src/types/matcher/csp-directive-matcher.ts`) - Matches one Content-Security-Policy directive by its **set** of source expressions rather than the literal header text. Ordering is tolerated; any difference in membership — added _or_ removed — is flagged, and the reason names which sources moved and in which direction. Removals are deliberately not tolerated: some CSP sources only suppress others while present, so dropping the nonce from `script-src 'self' 'unsafe-inline' 'nonce-…'` makes `'unsafe-inline'` live, dropping `'strict-dynamic'` makes a scheme-source match every origin, and a bare `require-trusted-types-for` is enforcement off. Use for CSP directives instead of an anchored `contentMatcher`, which mints a fresh near-duplicate alternative on every reorder. `'nonce-*'` is the only wildcard and stands for exactly one per-response nonce; host wildcards are not expanded (`https://*.example.com` and `https://a.example.com` are different assertions); directive names are case-insensitive per the CSP spec. Emitted for newly discovered `content-security-policy` values by `newHeaderValueMatcherConfig` (`src/utils/header.ts`), which `ScriptInventoryService` uses on all three header-writing paths. A whole-header `identifyWith` needs one `authoriseWith` alternative per directive, since identification is first-match-wins.
- **OrMatcher** (`src/types/matcher/or-matcher.ts`) - Composite matcher implementing OR logic (authorizes if ANY child succeeds, first-match-wins). Pure delegation: the only thing it fails secure on itself is a missing resource (`Resource is missing`) — there is no composite content pre-gate, because each child already fails secure on the evidence _it_ needs, and a blanket content check would have denied hash-only real-user observations before the `hashMatcher` alternative could accept them
- **AndMatcher** (`src/types/matcher/and-matcher.ts`) - Composite matcher implementing AND logic (authorizes only if ALL children succeed). Same delegation contract as OrMatcher: missing resource denies, missing content does not

**Evidence-Aware Fail-Secure Principle**: every matcher fails secure on **its own** missing evidence and nothing else — `hostMatcher`/`urlMatcher` on a missing `url`, `hashMatcher` on a missing `hash`, `contentMatcher` on absent content or an excerpt its pattern cannot soundly decide, `workflowMatcher`/`targetTypeMatcher` on a missing identifier — while composites delegate. Separately from evidence, **every** authorising matcher, leaf or composite, denies when its own `authorisationInfo.authorised` is `false` (FR-011): a leaf carries its own info as an array-syntax `authoriseWith` element or a composite child, and until 2026-10 five leaves (`name`/`url`/`host`/`initiatorHost`/`content`) ignored it, so a pending or declined alternative of those types authorised whatever it matched. Real-user observations are legitimately partial (a hash with no body, anchored windows instead of content), so a matcher that pre-gated on evidence it does not consume would deny them wholesale instead of letting the evidence they _do_ carry decide. `src/types/matcher/matcher.interface.ts` carries the per-matcher table.

**Important Distinction**: `NameMatcher` and `HeaderNameMatcher` are distinct implementations with different matching semantics:

- **NameMatcher** (for scripts): Case-sensitive URL/name matching (e.g., "https://Example.com" ≠ "https://example.com")
- **HeaderNameMatcher** (for headers): Case-insensitive name matching per RFC 7230 (e.g., "Content-Type" = "content-type")
- Both implement the same `Matcher` interface but with domain-appropriate behaviors

**Composite Matcher Nesting Recommendations**:

- **Tested Performance**: Up to 10 nesting levels without significant degradation
- **Typical Use Cases**: 2-4 nesting levels (e.g., CSP policies with multiple directive requirements)
- **No Hard Limit**: Deeper nesting is supported but may impact performance
- **Fail-Secure**: Empty composite matcher arrays are rejected at schema validation and constructor level
- **Metadata Paths**: Authorization metadata is collected from root to leaf for full audit trail

#### Authoring and Verifying Inventory Matchers

Two traps have each produced a matcher that looked correct, passed a hand-written check, and then never matched a single time in production — silently, for days, while the inventory lane papered over the gap. Both are worth knowing before writing an `authoriseWith` alternative:

- **`OrMatcher.authorize()` picks a child by `identify()`, not by trying each child's `authorize()`.** It takes the first child whose `identify()` returns true and authorises only that one (`src/types/matcher/or-matcher.ts`). So inside an `authoriseWith` array, an `andMatcher` alternative is skipped entirely when _any_ conjunct fails to **identify** — and the denial surfaces as the generic `No child matcher identified the resource`, which reads exactly like "this value isn't covered yet". When an alternative inexplicably never applies, test each conjunct's `identify()` in isolation before assuming the inventory is simply missing an entry.
- **A `urlMatcher` aimed at a _page_ must tolerate a query string and fragment** — end it `(?:[?#].*)?$`, never a bare `$`. Apps routinely reach a page through a redirect carrying something like `?return=…`, so a path-only end anchor can never match. (A matcher aimed at a script's own URL is different: those are exact, and a bare `$` is correct there.) This one is invisible in the auditor report, because `redactUrl()` renders `origin.url` as `origin + pathname` with query and fragment stripped — so a `Matchable` reassembled from report fields tests a URL shape production never emits.

Verify a new matcher by driving the real `createMatcher()` against content fetched from the live page, replicating `OrMatcher`'s identify-then-authorise selection, and include at least one URL carrying a query string. Never verify against a `Matchable` reconstructed from report fields alone. Assert the negatives too — the same body on another route, a lookalike host, a missing `url`, a prepended payload — since a matcher that authorises everything also "passes".

When reasoning about a run, three auditor-report fields have non-obvious semantics:

- `targets[].unmatchedInventoryEntries` lists entries that matched nothing in that pass. This is the evidence for retiring a stale entry — confirm it across every pass the entry is live for, and check the traffic isn't simply landing on a different target file.
- `observed.contentExcerpt` is a truncated prefix (`CONTENT_EXCERPT_LIMIT`, `src/services/report/mapper.ts`), so replaying report rows through content or hash matchers produces false negatives.
- `origin.url` is redacted as described above. For a script loaded from a `blob:` URL it reads `blob:https://<minting-host>/<uuid>` and `origin.host` is the minting document's host — before 2026-10-05 both were wrong (`https://hosthttps://host/<uuid>` and `(unknown)`), because `new URL()` reports a blob URL's inner origin as `origin` and the whole inner URL as `pathname`; an "obviously malformed" doubled-host URL in an older report or run log is this rendering, not a request the page made.

**A symptom worth recognising:** appending a hash for a genuinely new release is the normal, intended path. What is not normal is an entry collecting a _fresh_ hash on _every_ run: that means it identifies a payload which differs per request, so no hash can ever authorise it and the list grows without bound while verifying nothing. The tell is unbounded growth with no corresponding deploy. Establish which of the two you are looking at before appending another hash — the fix for the second is a matcher that authorises on the stable part of the payload, not one more hash.

**A `hostMatcher` in `authoriseWith` inventories a header without monitoring it.** In `identifyWith` a host matcher is the right tool — it pins an entry to a response origin. Repeated as the authorisation (`"authoriseWith": { "hostMatcher": "^vendor\\.example$" }`) it authorises whatever that host sends, so the entry can never produce a finding: the same matcher that authorises the real policy also authorises `connect-src 'self' https://exfil.evil.test`. The report shows such rows as `authorised` with a host-matcher provenance, which is exactly what a correctly working entry looks like, so this does not surface as a failure anywhere — the census counts it as covered. The tell is an **asymmetry between targets**: a third party's own policy change raises a finding on the target that pins the source set and is silent on the target that host-trusts it, so when two targets load the same vendor and only one ever alerts, read the quiet one's entry before tightening the noisy one. Narrow to a `cspDirectiveMatcher` per directive — but only against values actually observed, since a host with no observations has no set to narrow to and a guessed one alerts on the vendor's first real response instead of on a change. When one entry covers several hosts through a regex alternation, split it by editing the `identifyWith` host pattern rather than inserting a narrower entry in front of it: identification is first-match-wins, so an unedited alternation leaves the split depending on array order.

**When the changed header is served by the third party, attribution and authorisation are two separate questions — do not collapse them.** A vendor's own CSP arrives on the vendor's response, so the change was made by whoever controls that response — which is the origin, anything it fronts with, and anything on the delivery path, not necessarily the vendor. The URL names the serving endpoint; it does not name who modified the policy, so establish the delivery path before calling a change either the vendor's or a compromise of the vendor. That narrows the question but does not answer it: **is the host really the vendor's** (attribution), and **did the vendor intend the change** (authorisation). A compromised vendor origin serves attacker-modified policy from a host that attributes perfectly, so a correctly attributed origin is never on its own a reason to authorise — 11.6.1 is about the header as the browser receives it, whoever served it. Attribution is answerable from outside the monitor with RDAP for the registrar and registration date, `dig NS` for the delegation, and whether the added sources are subdomains of the host already serving the header; note a registrar is not the registrant, so each is corroboration rather than proof. Authorisation needs different evidence: the vendor's own documentation, release notes or changelog describing the change — the only kind that speaks to intent rather than ownership — plus whether the new sources could serve an attacker at all (a subdomain of the already-trusted emitting host, or a vendor property with no attacker-controlled content, gains an attacker nothing that owning that origin would not already give them) and **which browsing context the policy governs** — a vendor's CSP on its own cross-origin iframe document constrains that document, not the payment page, whose own CSP is a separate header to judge separately. Record in the entry's description what the documentation does **not** cover, so a citation for the host's existence is not read as a citation for the change. Two things are **not** evidence. First, that no request was observed to a newly added source: absence of traffic shows only that the permission went unexercised, and once the source is authorised a later request to it changes no header, so a `cspDirectiveMatcher` can never alert on that use — it watches the policy, not the traffic. CSP reporting does not close the gap either: it fires on requests that **violate** the policy — blocked under an enforcing policy, or allowed through and still reported under `Content-Security-Policy-Report-Only` — and never on requests that comply, and authorising a source is exactly what makes a request to it compliant. Treat an authorised `connect-src` source as a permission with no traffic-level monitoring behind it, which raises the bar on the questions above rather than lowering it. Second, omitting a source is not a remedy for a policy the vendor authors: dropping it from `allow` narrows the vendor's policy by nothing and only stops the entry matching what the vendor actually sends, so every run alerts forever. That lever is the vendor relationship, not the inventory.

**Some resources are structurally invisible to the inventory pass, so "not explained by staging" cannot be the bar for them.** A bot-mitigation challenge that only renders for production traffic, a geo-gated provider, a wallet button the runner is never eligible for: waiting for the staging pass to see these first waits forever. The available substitute is **cross-target corroboration** — two independent targets observing a byte-identical value across several consecutive runs — which shows the value is served consistently to unrelated pages, though not that it was deployed deliberately. It is weaker than staging corroboration, so pair it with vendor attribution before authorising, and say in the entry's description that staging cannot corroborate and why, so the next reviewer does not re-open a settled question.

**Retire a superseded CSP value instead of keeping it as an alternative** once no target has observed it for several runs. `authoriseWith` alternatives are a set of things that are still true; an alternative nothing serves any more only widens what the entry accepts. Confirm the old value is absent from every target and both passes — the report's per-row values, not `unmatchedInventoryEntries`, since an entry that still matches its other directives is not unmatched. One caveat on those row values: `value` is clipped at `MAX_REDACTION_INPUT` (8 KiB) by `redactForDisplay`, and the mapper keeps only the text, dropping the truncation flag it retains for `observed.contentExcerpt` (`src/services/report/mapper.ts`). A directive past that prefix therefore reads as absent when it is merely clipped, so for a value near that size confirm retirement against a full response capture rather than the row.

#### Transitive trust (initiator chains and load grants)

Policy this implements: _we validate our own scripts, and trust a vendor for what its authorised SDK loads_. Two inventory shapes, one piece of evidence.

**The evidence — `Matchable.initiatorChain`** (`src/types/initiator-chain.ts`): immediate inserter first, out to the root, at most `INITIATOR_CHAIN_MAX_DEPTH` (8) hops, each `script` (observed in this run), `document`, or `unknown` (named but not tied to an observation — nothing beyond it is assumed). On the synthetic lane `resolveInitiatorChains` (`src/services/initiator-chain.ts`) builds it after the run from each observation's first-hop evidence: hop 1 of an external script is its CDP initiator, of an inline script the attribution shim's record; from a script hop the walk continues with that script's own first hop. A URL observed with several initiators forks the walk (`alternateInitiatorChains`, capped at 16 paths); every path starts at the same immediate hop, which is exact evidence, so a match on any path counts. `initiator` keeps its long-standing URL meaning, and `chain[0].url === initiator` whenever the CDP top frame (below the shim's wrapper) names the inserting script. Two exceptions, both where that frame names no script (anonymous, or the document URL) and the shim's insertion log names the inserter instead: an **inline** inserter (`chain[0]` is the inline identity, `initiator` the document URL), and an **external script inserting from `eval`/`new Function` code** while it is `currentScript` (`chain[0]` is that script, `initiator` the document URL, since eval frames carry no URL). In both, the string-form `initiatorHostMatcher` sees the page host and the transitive form the inserter's.

**Inline hops.** The shim (`src/utils/page-attribution.ts`) gives every inline `<script>` a per-element instance token — at insertion, or the first time it is seen for parser-inserted markup — and records, for every script element inserted, which inline script (if any) was `currentScript` at the time. The shim is **not** tamper-proof: it lives in the page's own JavaScript world, so although `currentScript`/`src` are read through getters captured before any page script ran and the read API (`window.__pciAttribution`) is frozen and non-configurable, its records pass through built-ins page code can override, any page code can read every element's token, and an inline script can rewrite its own text after it has run — an adversarial review demonstrated each, and `/x/` in `test/integration/transitive-trust.test.ts` forges a record by overriding `WeakMap.prototype.get`/`has` and asserts the forged chain takes and still buys nothing. An inline hop's `url` is `inline_script/<name>#<token>`, and it resolves only through that element's own observation (a duplicate deduplicated away reads as `unknown`). For an **external** script, the shim's insertion log is consulted only when the CDP top frame names no script — empty (a dynamically inserted inline script or `eval`) or the document URL (inline code parsed from the page) — and only when every record for that `src` in that document agrees; a script URL in the top frame is never overridden by the log. Neither source is unforgeable either: a call frame's URL is the script's name, which `eval`'d code can choose with `//# sourceURL`. Only the nodes being **inserted** are recorded (a `DocumentFragment`'s script descendants included), never `insertBefore`'s reference node or the node `replaceChild` removes: the classic loader snippet passes the page's first `<script>` as the reference, and recording it would attribute a parser-inserted script to the loader. `src/utils/page-attribution.test.ts` evaluates the shim string in jsdom for the cases the real-Chrome pages do not reach (async insertion → `none` → an `unknown` first hop, fragments, `insertAdjacentElement`/`replaceChild`, the captured `currentScript` getter); jsdom clears `currentScript` after a nested script runs instead of restoring the outer one as Chrome does, so drive one insertion per inserting script there. Limits, each failing towards _less_ trust: frames' inline scripts and insertion logs are not read (only the top-level document is scanned), so an anonymous initiator inside a frame is `unknown`; an async insertion with no `currentScript` is `unknown`; `document.write` markup reads as parser-inserted (document).

**Trap — the shim's own frame.** The shim wraps `appendChild`, so Chrome reports the wrapper as the **top call frame** of every request a DOM insertion triggers, with an empty URL. Until a real-Chrome test caught it (2026-10-06) `deriveInitiatorUrl` therefore fell back to the page URL for nearly every dynamically inserted script, and a synthetic `initiatorHostMatcher` silently matched the page host instead of the loader's. The shim now carries a per-attempt random `//# sourceURL` and `topCallFrameUrl` (`src/handlers/script.ts`) removes exactly one leading frame with that URL (a second one reads as anonymous, never as its caller). Probe what Chrome actually reports — `request.initiator()` — before trusting any reading of a call stack; a unit test with a hand-written stack would never have shown this.

**Shape 1 — transitive `initiatorHostMatcher`** (see the Matcher System entry above).

**Shape 1b — trust through a vendor's frame documents (`kinds: ["document"]`).** Scripts inside a payment provider's nested frames are loaded by the _frame document_, and a `document` hop ends a grant walk, so a provider's `authorisesLoads` never reaches them. A transitive `initiatorHostMatcher` with `kinds: ["document"]` on the vendor's hosts, ANDed with a `nameMatcher` on the script's own URL (README has the pattern), identifies and authorises them instead. **Trap — a `document` hop in a chain is not browser evidence.** The hop _kind_ comes from the resolver, which classifies a URL as a document by equality with a document URL the run loaded, and reaches a document by walking page-forgeable script hops. A real-Chrome test (`/k/` in `test/integration/transitive-trust.test.ts`) forges both ways from the payment page with one `eval` each: `//# sourceURL` naming a script the vendor frame loaded (the walk continues to the frame's document — the chain reads `script:frame-host/… ← document:frame-host/…`), and `//# sourceURL` naming the frame document's URL from a timer (no `currentScript`, so the shim names nothing and the stack URL is classified as that document). Matching `kinds: ["document"]` on chain hops alone — the obvious implementation — is satisfied by both; removing the binding in `InitiatorHostMatcher.considers` makes exactly those two tests fail. What page code cannot forge is the frame a request is _issued from_, so a document hop counts only when its origin is that frame's: `ExternalScriptSource.frameUrl` is the frame's URL recorded on `request` (detection's `issuedFrameUrls`) and read again on `response` before any `await`, and the two readings must agree on origin — a frame the page navigates to the vendor's document after sending the request binds nothing. A real-Chrome probe (2026-10-06) found Chrome aborts such a request anyway (`net::ERR_ABORTED`, no response), and `/k/`'s race case asserts it is never authorised either way; the request-time reading keeps the binding from depending on that browser behaviour. Two consequences, both fail-secure: capture and payment-scope collapse keep one copy per (url, hash), so when copies of one script come from frames on different origins (or one has no frame) the kept copy's `frameUrl` is dropped (`agreedFrameUrl`) — otherwise the page loading the vendor's own script could ride the frame copy's binding; and inline scripts (only the top-level document is read), workers and every real-user observation carry no `frameUrl`, so `["document"]` never matches them. `consumesOnlyUrlEvidence` treats an `initiatorHostMatcher` whose kinds exclude `script` as not URL evidence, so on the RUM lane such an authoriser leaves the observation identification-only instead of raising a false mismatch. Never aim it at the payment page's own host: every script on the page is loaded into that document.

**Shape 2 — `authorisesLoads` on an authorised script entry**: `"direct"` (depth 1) or `"transitive"` with optional `maxDepth` (1–8, default 8), and a **required** `loadsMatching` matcher config applied with `identify()` to the loaded script. `ScriptComparisonService.compare` runs two passes: pass 1 judges every script as before; pass 2 (`inheritAuthorisation`) walks each still-`unknown` script's chain outward and authorises it (`AuthorizedScriptFound` with `inherited: { from, via, mode }`) at the first hop whose every observation is an **external** script pass 1 **explicitly** authorised under an entry granting at that depth, provided the loaded script passes the guard. Fail-secure rules, each with a unit test in `src/services/comparison/inheritance.test.ts` that was checked by breaking the rule and watching it fail, and the main ones end to end in `test/integration/transitive-trust.test.ts`:

- **Only `unknown` inherits** — an identified-and-denied script stays denied (guarded twice, in the result map and in `inheritFor`; only removing both fails the test).
- **An entry pending review or declined is a verdict too** — pass 1 skips unauthorised entries, so their scripts reach pass 2 as `unknown`; the `identified` predicate deliberately consults **every** entry, whatever its `authorised` flag, so a reviewer's "not yet" or "no" is never overridden by a grant (detection keeps alerting; the inventory pass sees the script as already proposed).
- **An inline load never inherits** — the mirror of "an inline script never grants": its name is its element id or the shared fallback, and its chain is what the forgeable shim recorded. An inline script is authorised by an entry on its content or hash, and then carries the walk for what it inserts.
- **A mismatched root poisons its subtree** — the granting hop must be authorised in this run, every observation of it (the walk cannot tell which copy did the loading); identified-but-denied is not authorised.
- **Pass-through needs authorisation** — a hop that does not grant at that depth is crossed only if it is itself authorised (explicitly or by inheritance); a denied, un-inherited or absent intermediate stops the walk.
- **A broken chain stops inheritance** — the walk ends at the first `document`/`unknown` hop; no chain inherits nothing; a cycle in the evidence cannot vouch for itself.
- **Only an authorised entry grants** — `RawInventoryScriptInfoSchema` (so `--mode validate`) refuses `authorisesLoads` on an entry whose `authorisationInfo.authorised` is not `true` (for array syntax, the first element's, which is the entry-level info), `maxDepth`/`loadsMatching` without a grant, and `maxDepth` on a direct grant; the comparison re-checks `authorised` anyway.
- **`loadsMatching` is mandatory, judges the load itself, and an inline script never grants.** Chain evidence is not unforgeable by code already on the page (above), so a grant must always be checked against the one thing the page cannot forge — the loaded script's own URL. Name hosts that serve only the vendor's own code: a guard over a public CDN anyone can publish to buys nothing. Validation refuses a guard that cannot tell one load from another: every OR alternative needs a `nameMatcher`/`urlMatcher`/`hostMatcher`/`contentMatcher`/hash list and an AND at least one such conjunct (`workflowMatcher`/`targetTypeMatcher` match run metadata every script shares; `initiatorHostMatcher` reads evidence `ownEvidence` drops), and a `nameMatcher` that would admit an `inline_script/` name (probed, plus a literal check) — it would claim something the comparison never does. An inline granter is refused outright because its text at scan time need not be the code that ran. The guard sees only the loaded script's own evidence (`ownEvidence`): `initiator` and chain are dropped before it runs. A script some entry identifies never inherits, even when it reached pass 2 as `unknown` (the synthetic empty-content gate runs before identification). An inline hop resolves only through the element's own observation; a duplicate collapsed into another observation was never judged on its own and reads as `unknown`.

What the transitive `initiatorHostMatcher` without `kinds` sees: every known hop, `document` hops included and unbound — so a pattern that matches the page's own host identifies **every** script on the page, exactly as the string form does for parser-inserted tags. Use it for vendor hosts, pair it with an authorisation that checks content, and remember that host evidence is as forgeable as the chain. Static ES-module imports carry no call stack, so their first hop is `unknown` and a module graph never chains.

An inherited row is evidence like any other: it keeps its hash and chain in the census, it never feeds the inventory diff (it is not `unknown`), and the report cites the grant. Decide deliberately how the granting entry itself authorises — a hash makes any change to the SDK cut its loads off; a URL trusts the vendor's release process.

#### Comparison Result Types (Enhanced 2025-10 with Metadata Paths)

**Script Comparison Results:**

- **UnknownScriptFound** (`src/types/comparison/unknown-script-found.ts`) - Script not in inventory or has null/empty content
- **KnownScriptWithUnauthorisedContentFound** (`src/types/comparison/known-script-unauthorised-content-found.ts`) - Script identified but authorization failed (includes matcher details, failure reason, and metadataPath for composite matchers)
- **AuthorizedScriptFound** (`src/types/comparison/authorized-script-found.ts`) - Script both identified and authorized (compliant, no alert; includes metadataPath for composite matchers). With `inherited` set it was authorised by a load grant instead (see _Transitive trust_): `inventoryEntry` is then the **granting** entry, whose `identifyWith` never identified this script — the report shows `identification: null` and cites `grantedBy`
- **MissingRequiredScript** (`src/types/comparison/missing-required-script.ts`) - Script entry configured with `requiredOn` for the current pass (`inventory`/`detection`) but no detected script was identified by its `identifyWith` (potential control removal — e.g. the RUM monitoring agent stripped from a payment page). Presence only: integrity of a present script stays with ordinary hash authorisation. Synthetic passes only, judged against the entry itself rather than first-match-wins attribution. On the **detection** pass it alerts to `detection.missingScriptDetected`, falling back to `scriptMismatchDetected`; on the **inventory** pass it routes to `inventory.newScriptIdentified` instead. `requiredOn` only arms for **authorised** entries (`authorisationInfo.authorised === true`): a pending/unauthorised entry's `requiredOn` is inert, because a candidate is flipped to `authorised: true` only after human review, and until then its absence is not yet a control removal

**Header Comparison Results:**

- **UnknownHeaderFound** (`src/types/comparison/unknown-header-found.ts`) - Header not in inventory
- **KnownHeaderUnauthorisedContentFound** (`src/types/comparison/known-header-unauthorised-content-found.ts`) - Header identified but authorization failed (includes matcher details, failure reason, and metadataPath for composite matchers)
- **AuthorizedHeaderFound** (`src/types/comparison/authorized-header-found.ts`) - Header both identified and authorized (compliant, no alert; includes metadataPath for composite matchers)

Platform-level canonicalising 308s typically carry neither CSP nor `x-frame-options`, so a workflow that crosses one will still trip a required XFO or `x-content-type-options` — navigate canonical URLs in workflows

### Unread script bodies

`Could not load response body for this request. This might happen if the request is a preflight request.` on a script is almost never about preflight. It is Puppeteer's rewording of `Network.getResponseBody` failing with `No resource with given identifier found`, and the usual cause is navigation: Chrome holds a document's response bodies in the renderer and discards them once a navigation away from that document is under way, so every script that **finishes loading between a click and the navigation it triggers** is unreadable — on a payment page, exactly the scripts a "Pay" click pulls in on its way to 3-D Secure, which is also when a skimmer would load. Reading sooner does not help (the read already starts the moment the response arrives); the fix is `Network.configureDurableMessages`, which keeps bodies outside the renderer so they survive the navigation. The setting belongs to the DevTools **target**, not to the session that sends it, so the dedicated session `retainResponseBodies` opens on the page is enough for Puppeteer's own reads of the page's bodies. An **out-of-process iframe is a target of its own** — any cross-site frame under site isolation, so every card provider's hosted fields and 3-D Secure challenge — and the page-level setting does not reach it: a script that finishes loading as such a frame navigates _itself_ on (a "Pay" handled inside the provider's frame) fails with exactly the same `Could not load response body` error, which is how the first production run after the page-level fix still went red. `frameBodyRetention` sends the same command on each frame's own session — the one Puppeteer reads that frame's bodies through, `Frame.client`, which is not in Puppeteer's typed API and is read through the guarded `frameSessionOf` like the ledger's `HTTPRequest.id`/`Frame._id` — on `frameattached`, on `framenavigated` (in case a navigation gives the frame a new session) and on every request, once per session. The command reaches a frame's session only after Puppeteer has attached it and let the frame run (on `framenavigated` or the frame's first request), so a frame's very earliest resources may load before retention is on; a body lost that way lands as unread (red), never fail-open. A probe (2026-10-05) found that when an out-of-process frame navigates to another cross-site origin (`localhost` → `[::1]`), Puppeteer keeps the same session object and the retention set on it survives the navigation, so the once-per-session dedupe is safe; a genuinely new session (the swap `framenavigated` guards against) was not observed in current Chrome and is covered by a unit test only. Both kinds of session also report Chrome's raw `Network.loadingFinished` to `PendingScriptReads` (the page's through the dedicated session, an iframe's through Puppeteer's own), the backstop described under _Partial runs_. When reproducing this, remember that **different ports are the same site**: a test frame needs a different host (`127.0.0.1` for the page, `localhost` for the frame) to get its own process at all. A body that is still unrecoverable — the frame torn down before the read, which reads `Session closed. Most likely the iframe has been closed.` — is recorded as unread rather than lost (see _Partial runs_). Three details of that drain each closed a hole a review found: **requests are tracked as well as reads** — a script requested by the last step has no read to wait for yet, so without this its response landed while the context was closing and the handler recorded it into an array the summary no longer read, logging it as recorded while it was lost; **the run is sealed after the drain** — a body that finishes reading afterwards is recorded as unread, never compared, so it cannot be both compared and listed; and **records are deduplicated by URL, document and status, not reason** — the same gap is seen twice, as unfinished at the deadline and again as `Session closed` when the context closes. `test/integration/unread-scripts.test.ts` drives these paths in real Chrome: the navigation case (commenting out the `retainResponseBodies` call makes every late script fail with the production error and the run exit 2 with each one named), the same inside a cross-site iframe that navigates itself away (replacing `retainFrameBodies` with a no-op does the same for the frame's scripts), and the deadline case, with one script whose body never finishes and one whose response never arrives, asserting exactly one `unansweredRequests` record each and exit 0. Both land as unanswered requests, and that is why they no longer fail the run: in the observed Chrome behaviour, **Puppeteer's `response` event for a script fires only once its body is complete** (the probe below), and a classic script cannot execute before its body is complete either, so a request with no response and no sign its body finished never ran on the page. The backstops under _Partial runs_ are what make that safe to rely on. (Two production records of this kind — a script URL the page had built by concatenating its origin twice, and a CDN request issued mid-workflow — had turned an otherwise clean run red; both plausibly came from torn-down frames, whose requests Puppeteer does not always report as finished or failed. So `PendingScriptReads.frameDetached` stops the deadline being spent on a detached frame's requests. When Chrome aborts them and Puppeteer reports `requestfailed`, that takes them off the wait and off every list — nothing was delivered. Only a request that gets neither a finish nor a failure is listed, with the detached-frame reason — which is what a probe (2026-10-05) saw for an out-of-process frame the page removed: no `requestfailed`, only `framedetached`. A response that lands for one anyway is read — or, after the seal, recorded as unread. A request still outstanding as the context closes can carry that same detached-frame reason, since closing the context detaches its frames.) The integration suite also removes a cross-site frame while it has a script request outstanding — in a later step than the one that issued it, with one more step after, so the record's `detachedAtStep` is distinguishable from both the issuing step and the last step (reading the step at issue time instead makes it fail). No deterministic real-Chrome construction was found for a body that completes inside the close grace after the seal, for an OOPIF torn down between response and read, or for a `requestfinished` without a response; those paths are covered by unit tests in `src/handlers/script.test.ts` and the wiring tests in `src/services/detection.test.ts`, each checked by breaking the code and watching the test fail. A real-Chrome probe (2026-10-02) showed `Network.responseReceivedExtraInfo` at headers time but the renderer's `Network.responseReceived` — the one Puppeteer builds the response from — arriving together with `loadingFinished`, at 2 s for a body held back 2 s and never for one that never ends, a stalled chunked body, a 64 KB partial chunk and a short `content-length` alike. So a script still streaming when the workflow ends is a request with no response, the `reading` branch of the deadline covers only DevTools round-trip latency, and the bodies the navigation case lost were complete when they were lost — evicted, not truncated.

### Workflows

Workflows are defined as step-by-step instructions for Puppeteer in `src/workflows/`:

- Each step includes element selectors and actions (click, input, navigate, totp)
- `waitFor` selector types: `div` (class), `button`/`h2`/`h3`/`span` (visible text, substring match), `input` (name attribute), `href` (link suffix), `testid` (`data-testid` attribute — preferred when the target app exposes test ids), `aria` (`aria-label` attribute — for icon buttons with no visible text), `id` (`id` attribute — for hosted payment iframes whose fields carry no `name`, e.g. Toast's `credit_card_number`). Set a step's optional `frameUrl` regular expression to resolve and act inside a dynamically mounted child frame; anchor it to a trusted HTTPS origin and stable path.
- Target URLs may embed `{{date}}` / `{{date+Nd}}` placeholders (`src/utils/date-template.ts`), resolved to a UTC `YYYY-MM-DD` at navigation time — for booking-style targets whose availability requires a future date
- Steps are converted to PuppeteerLocatorActions for execution
- Support for popup handling and complex user flows
- Whole-workflow recovery is bounded and fail-secure: retry only recognised transient browser failures in a fresh context, discard observations from the failed attempt, and never replay after a side-effect boundary. A click with `waitForResponse` is a boundary automatically; add `retryBoundary: true` to any other step whose dispatch may have an irreversible or externally visible effect. Keep `maxAttempts` between 1 and 3.
- **A `frameUrl` step that times out with only the top-level document under `Observed frame URLs` is not a selector problem.** The hosted payment frame was never mounted, and the application decides that, not the workflow: the pattern seen so far is the app's own session-creation call to its backend failing with a 5xx right after the preceding click, which the page renders as a generic "could not load the card form" message that leaves the SPA on its current route. The failure sits before any retry boundary, so whole-workflow recovery does run — and the second attempt fails identically, which is the tell that the cause is deterministic and that editing the workflow, adding delays or raising `maxAttempts` changes nothing. Diagnose by replaying the preceding steps in a local Puppeteer probe that records, for the app's payment-gateway API only, the response status, request method and the problem-detail fields of a failed response (`status`, `title`, `traceId`) — never the body of a successful response, which carries provider tokens and session secrets, and never in CI — then check whether the production counterpart still mounts the frame; if it does, the fault is staging-side and the fix belongs with the application or provider sandbox. The run itself carries on without that variation (see _Partial runs_ under CLI Usage): the other targets in the pass still run, the inventory push still happens under `--mode inventory` and `--mode all`, the detection pass still follows under `--mode all`, the run summary names the failed target, and the process exits 2 — so the evidence gap is confined to the one page, not the whole day.
- `totp` actions type an RFC 6238 one-time code (6 digits / 30s, `src/utils/totp.ts`) generated at step-execution time. The step carries only a `seedRef` name; the base32 seed is supplied at runtime via the repeatable `--totp-seed <name>=<seed>` parameter and must never be committed to the inventory repo, logged, or included in alerts. If fewer than 5 seconds remain in the current window, execution waits for the next window before generating the code.
- **`paymentPage: true` scopes the run to the payment page's SPA context.** Mark the top-level step whose `waitFor` only exists on the card-entry page. The payment document is the top-level document in which that step's target was found — read _before_ its action runs, so a "Pay" click that navigates away cannot move the marker onto the next page. Scope is the browser's own document boundary (Chrome `loaderId`, tracked by `DocumentLedger`, `src/services/document-ledger.ts`), not URLs or steps: a client-side route change keeps the document, a full navigation creates a new one, so everything an earlier SPA route loaded into the payment document is in scope. `outsidePaymentDocuments` is the single definition of what leaves scope: an earlier document leaves only when it **never rendered a payment path** (its commit URL _and_ every route it reached by same-document navigation — `DocumentLedger` records `Page.navigatedWithinDocument` into `routes` for exactly this), **was never current at or after the first payment document** (a back/forward-cache restore reuses the old `loaderId`, so the same id can reappear after payment), **and, if the monitor's own reload recovery replaced it, was replaced by a document that is itself outside** (recovery can land on a different path, e.g. a start URL that redirects to a per-visit session path, so detection records every document it replaces, on every step, via the `onRecovery` hook on `waitForRecoverableActionTarget` / `waitForInitialActionTarget` / `navigateToTarget`; a replaced render takes the scope of the next document in the chain, resolved to a fixed point because recovery can replace a render recovery produced; if the replaced document cannot be read the run is left unresolved). The payment document itself is read by `resolvePaymentDocument`, which brackets the read — document, target still present (or found element still attached), document again — so a navigation committing just after the target was found cannot mark the next page as the payment page. That bracket is exact for framed steps, which keep the element the wait found; for a top-level step it re-runs the selector, so it relies on the documented requirement that the marked step's target exists only on the card-entry page — if it held, any page matching it is a render of the payment page and stays in scope by the path rule anyway. Everything else stays in: every document after the payment page, a failed render of the payment page that reload recovery replaced whether it was loaded at or routed to the payment path, and any document missing from the chain. Two review rounds each found a fail-open in a looser version of this rule — "only the marked documents are in scope" silently scoped out every navigation after the marked step, and comparing commit URLs alone scoped out an SPA render that had routed to checkout before reload recovery replaced it — so treat any narrowing of it as a fail-secure change that needs a real-Chrome test. `partitionByPaymentScope` (`src/services/payment-scope.ts`) splits the detection summary before comparison: the payment part is compared, alerted on and fed to the inventory diff exactly as a whole run used to be; the outside part is compared by `compareOutsidePayment` for the auditor report only — never alerted, never inventoried, presence (`requiredOn`) checks skipped, every log line prefixed `[outside payment page]`, and it never throws. **Fail-secure invariants worth preserving:** an observation leaves scope only when attributed to a _known non-payment_ document — unattributed observations (worker requests, frames never seen attaching, a Puppeteer build without the internal `HTTPRequest.id`/`Frame._id` the ledger reads) stay in; if any marked step's document cannot be read, the whole run stays in scope rather than scoping to the documents that did resolve; and capture dedupes scripts by `(url, hash, document)` / `(hash, document)` so the payment page's copy of a script an earlier page also loaded survives (the partition collapses back to the old keys within each scope, so unmarked workflows compare and alert exactly as before). Once scoped, `requiredOn` presence is judged against the payment-scope partition (the payment document, everything after it, earlier renders of a payment path, failed renders recovery replaced with an in-scope page, and unattributed observations), so a required control found only on an earlier page that left scope no longer satisfies it. A marked payment page that cannot be identified falls back to whole-run scope and is recorded in the report as `paymentScope.resolved: false`. Popup steps cannot carry the marker (popups are not observed)

## Scheduled Execution

The daily run is scheduled from the **inventory repository**, not from this one. The auditor report's artefact contains the inventory verbatim, and this repository is public, so a scheduled run here would publish a private inventory. This repository keeps `workflow_dispatch` and `push: main` — both still full production runs, not dry runs.

- **Daily execution** at 12:00 PM UTC, from the inventory repository's own workflow
- **Inventory pass** runs first to update baselines
- **Detection pass** follows to monitor against updated inventory
- Only one repository should hold the schedule: two would run concurrently against the same inventory, and two `--mode inventory` passes would each push `inventory-updates` and open a PR
- **The `ghcr.io/puppeteer/puppeteer` image tag must track the `puppeteer` version in the tool's `package-lock.json`**, not its `package.json` caret range: the image ships exactly one Chrome build, and a mismatch kills the run at browser launch — roughly a minute in, with `Could not find Chrome (ver. <n>)` naming a cache path that is present but holds a different build. Because the scheduled run's workflow lives in the inventory repository while the lockfile lives here, that repository's Renovate cannot see the bump that invalidates its pin, so every tool-side Puppeteer upgrade turns the schedule red until someone bumps the tag by hand. Derive the container tag from the tool's lockfile at run time (a small `needs:` job whose output feeds `container.image`) and check out the tool at the same commit the version was read from, rather than pinning the tag in two repositories and hoping they move together

## Build System

- **Module system**: native ESM (`"type": "module"`). Relative imports must
  carry explicit `.js` extensions (`./foo.js`, `./bar/index.js`); SWC emits ESM
  to `dist/` and the app runs via `tsx`. Config/utility files that stay
  CommonJS use the `.cjs` extension (`eslint.config.cjs`, `jest.config.cjs`,
  `scripts/migrate-inventory-schema.cjs`).
- **TypeScript compilation**: SWC via `@swc/cli` (config in `.swcrc`)
- **Linting**: ESLint flat config (`eslint.config.cjs`)
- **Formatting**: Prettier (config in `package.json`)
- **Testing**: Jest 30 with `@swc/jest` transform (`jest.config.cjs`); a
  `moduleNameMapper` strips the `.js` extension so tests resolve `.ts` sources
- **Type checking**: `tsc --noEmit` directly

## Behaviours

- **Keep public examples generic**: This is an open-source project. Never add organization-, customer-, venue-, or deployment-specific application details to source comments, documentation examples, tests, fixtures, sample workflows, or sample inventories. This includes real hostnames, URLs, venue/account identifiers, email addresses, internal repository names, and copied production policies. Use clearly fictional names and RFC-reserved domains such as `example.com`, `example.org`, and `.test`. Public payment-provider names and their documented public endpoints may be used when the behavior is genuinely provider-specific. Authoritative project ownership, licensing, repository, and security-reporting metadata are not examples; do not rewrite them without explicit maintainer direction.
- **Never merge PRs without human review**: Do not merge any pull request that has not been reviewed and approved by a human. `main` branch protection requires a code-owner approval — do not bypass it. Specifically, never use admin/override merges (e.g. `gh pr merge --admin`) or otherwise circumvent required reviews and status checks. You may prepare a PR so it is ready to merge (fix CI, resolve conflicts, push), but a human must perform or explicitly authorize the final merge.
- **Commit messages**: Please use conventional commits and keep them concise. Tell us what value was created in the commit, not a catalog of changes.
- **Code review on commit**: Before creating a commit, run `/coderabbit:review --base main` and address its findings (or explain why a finding is intentional) as part of the same change. Treat CodeRabbit as a required review step alongside `npm run precommit` — precommit verifies correctness, CodeRabbit catches design/quality issues a static check won't.
- **CodeRabbit PR reviews are asynchronous**: passing the pre-commit CLI review is not the end of the CodeRabbit step. After opening a PR or pushing new commits to one, CodeRabbit posts inline review comments on the PR **5–15+ minutes later** — check for them before considering the work done (`gh api repos/<org>/<repo>/pulls/<n>/comments`, filtering `in_reply_to_id == null` for top-level findings, and `original_commit_id` for which commit raised them — see the round-verdict traps below). Silence shortly after a push means the review hasn't run yet, not that it found nothing. **The canonical per-round completion marker is the `Actionable comments posted: N` line in the latest `coderabbitai[bot]` entry of `/pulls/<n>/reviews`** — verified against this repo, 2026-08-07:

```bash
gh api --paginate --slurp repos/<org>/<repo>/pulls/<n>/reviews | jq 'add | [.[] | select(.user.login == "coderabbitai[bot]")] | last | {submitted_at, marker: (.body | split("\n")[0])}'
```

A clean round may instead land as a review whose `state` is `APPROVED` with an **empty body**, so key a watcher on a new `coderabbitai[bot]` review appearing and read its `state` plus first body line together — a watcher that prints only the marker shows `null` for the approval and looks stuck. On some repositories a clean round leaves **no review object at all**: the only verdict is the line `No actionable comments were generated in the recent review` inside the summary issue-comment, with zero inline comments. So a round is complete when any one of these appears after your push, each from `coderabbitai[bot]` and none from a human or another bot: a new review (read its `state`), that sentence in the summary comment, or new top-level inline comments. One more terminal state to match: the summary comment can instead say **`Review limit reached`** (the plan's hourly allowance of included reviews is spent, and every refused attempt lowers the rolling allowance further) with a "wait N minutes" hint; nothing was reviewed, no round will arrive on its own, and the trigger comment has to be posted again once the window has passed. Do **not** grep the summary issue-comment for the `Actionable comments posted` phrase: CodeRabbit now renders a "Review Change Stack" walkthrough there instead, so the phrase never appears and a watcher keyed on it waits forever. The summary comment is still edited in place per round, so its `updated_at` is a usable _change_ signal; read the verdict from the review object when the round produced one, and from the summary comment's sentence when it did not. While a round is running, the summary comment contains `review in progress`. Counting new inline comments is still unreliable on its own: a clean round adds none. Poll with a persistent Monitor keyed on that marker rather than a fixed-window loop that gives up — CodeRabbit is frequently slow (10+ min, occasionally ~50 min), and rounds that land after a fixed window are silently missed. Compare timestamps in a single timezone (its `Z`, not a local `+NN:00` offset). Address or rebut every finding and reply on its thread with the fix commit. On repos with auto-review enabled, every new push triggers a fresh review round automatically; re-check after each push until a round comes back clean.

- **Three traps in the polling itself** (all met on 2026-09-08): `gh pr comment <n>` and `gh api` resolve the repository from the **current directory** — with the engine and the inventory repo both checked out, and a harness that resets the cwd between commands, a trigger comment can land on the _other_ repo's PR of the same number (it did: a merged Renovate PR got a review round). Always name the repository explicitly: `--repo <org>/<repo>` on `gh pr …` (and `gh run …`), and a fully qualified `repos/<org>/<repo>/…` endpoint on `gh api`, which has no `--repo` flag. `gh api .../issues/<n>/comments` and `/pulls/<n>/reviews` return only the first 30 entries (oldest first) without `--paginate`, so once a PR passes 30 comments every "anything new since X?" check silently sees nothing — a monitor sat blind for an hour. Always `--paginate` those listings — and because `--jq` runs per page, aggregate first (`--paginate --slurp … | jq 'add | …'`) before taking `last`, as the command above does. And `@coderabbitai review` placed in the same comment as a reply to a finding is treated as the reply, not the command (the bot answers the reply and no round starts) — post the trigger as its own comment.

- **Six ways a finished-looking round lies** (all met 2026-09-30 – 2026-10-02; each made a watcher report a verdict that was not one):
  1. **Key on the head SHA, taken from your own push.** CodeRabbit emits several review objects around one round, each carrying the `commit_id` it reviewed — an earlier `APPROVED` turns `DISMISSED` when you push, and empty-bodied `COMMENTED` objects for the superseded commit arrive alongside — so a watcher keyed on "a new review appeared" or `submitted_at > <push time>` reports the old commit's verdict as the new one. Match `commit_id` against `git rev-parse HEAD` after the push, and ignore `DISMISSED`. Do not read the head from the API instead: right after a push `gh api repos/<org>/<repo>/pulls/<n> --jq .head.sha` can still return the previous head (with `mergeable: false`) for several seconds, and a watcher seeded from it watches a commit that is already history.
  2. **A rate-limited round leaves a green check, and the refusal shows up in one of two places depending on what triggered the round.** An _automatic_ round (a push on a repository with auto-review) that is refused edits the summary comment to `Review limit reached` and sets the `CodeRabbit` status check to `pass` with the description `Review rate limited` (seen on this repository, 2026-09-30). A _manually requested_ round (`@coderabbitai review`) that is refused gets a short reply, `⚠️ Action not completed — Review rate limited`, while the status check keeps whatever it said for the previous round — often a green `Review completed` (seen on the inventory repository the same day). So a watcher must check all three — the status check description, the summary comment, and the latest short bot reply — and treat any one of them saying rate limited or limit reached as "this head is unreviewed". Nothing will run on its own; a merge on that green check is a merge of unreviewed code. The allowance is shared across the organisation's repositories, so pushes to one PR can spend another's.
  3. **Read the verdict from the summary comment, not the last comment.** The summary is the long comment created first and edited in place; `last` by creation order is usually a short trigger acknowledgement — which is exactly where the rate-limit refusal appears, so a watcher reading `last` for the summary misses both.
  4. **Count new findings by `original_commit_id`.** When a push leaves a commented line intact, GitHub re-anchors the existing comment to the new head — its `commit_id` moves, its `original_commit_id` stays — so filtering on `commit_id == head` reports an answered finding as new.
  5. **A short SHA never matches.** The API returns full 40-character SHAs; compare against `git rev-parse <ref>`, never a hand-typed abbreviation, or the watcher waits forever.
  6. **The summary's clean verdict outlives the round that produced it.** The `No actionable comments were generated` sentence is written into the summary comment by one round and is not cleared when the next round starts, so immediately after a push the summary still reads clean for the _previous_ head — a watcher that reads only that sentence reports the new commit as reviewed before anything has looked at it. Pair the sentence with the commit the summary itself names (its hidden metadata carries the reviewed commit SHA; the walkthrough block names it too) and accept the verdict only when that SHA equals `git rev-parse HEAD` — and not even then on its own: the summary is rewritten to name the new head the moment a round _starts_ for it, while the stale sentence stays until the round rewrites it, so a watcher saw "clean, names head" with the status check still reading `Review in progress` (2026-10-02). Require a terminal signal as well: a non-dismissed review object whose `commit_id` is the head _and_ whose `submitted_at` is later than your push or trigger comment — after an `@coderabbitai full review` the same commit is reviewed again, so an older object already matching the head is last round's verdict, not this one's — or the `CodeRabbit` status check reading `Review completed` _while_ the summary no longer says `review in progress`, since the status check alone can still be last round's too (trap 2).

  Pushing small follow-up commits into a rate-limited queue costs reviewed state: each push dismisses the last approval and needs a round the allowance may not have. Batch prose fixes from a review into one commit, or into a follow-up PR.

- **Resolve CodeRabbit threads after the final reply round — replying is not closing.** CodeRabbit auto-resolves threads it sees fixed, but a thread answered with a decline/rebuttal (and occasionally a fixed one) stays unresolved forever. Once every thread is either fixed-with-commit or rebutted on-thread, comment `@coderabbitai resolve` on the PR: it resolves all remaining CodeRabbit threads within about a minute. Verify with GraphQL (`reviewThreads(first: 100) { nodes { isResolved } pageInfo { hasNextPage endCursor } }` on the pull request, following `hasNextPage`/`endCursor` — the connection caps at 100 nodes per page, and an unpaginated check can false-pass a large PR) rather than assuming; do this even on an already-merged PR so the review record closes cleanly. Never use it to bury an unanswered finding — every thread must carry its fix reference or rebuttal first.

- **Do not merge a PR before its CodeRabbit round has returned**: merging while a review is still in flight strands the findings on a merged PR and forces a follow-up PR for every fix. Only mark a PR ready to merge once the latest push's round has landed and come back clean (or every finding has been addressed/rebutted on-thread).
- **Repos with auto-review disabled**: CodeRabbit posts a "Review skipped" notice instead of reviewing, and pushes never trigger rounds automatically. Comment `@coderabbitai review` on the PR to trigger a round — after every push, since nothing runs on its own — then wait for it like any other round. Do not assume the mode per repository: a repository that once behaved this way can later auto-review a new PR on open and then auto-pause it ("Reviews paused … branch is under active development"), and a `@coderabbitai review` posted after such a round answers `Already reviewed the last commit` and runs nothing. Read the latest CodeRabbit notice on the PR for the current commit to learn which mode you are in now — the first comment is history, and the mode can have changed since; after a pause, `@coderabbitai review` reviews only new commits and `@coderabbitai full review` re-reviews everything.
- **Always link PRs, issues, and CI runs every time they are mentioned**: every reference in a chat response, PR description, or comment must carry its own clickable full URL (or an auto-linking `owner/repo#N` form) in that same message. Repeat the link on later mentions instead of relying on an earlier message or nearby context; never use a bare number that makes the reader scroll or search for the link.
- **2nd code review on commit**: Before creating a commit, run the vendored `branch-review` skill (`.claude/skills/branch-review/SKILL.md`) over the pending change — the `staged` scope for a commit, the whole branch before opening a PR — and address its findings (or explain why a finding is intentional) as part of the same change. Treat this as a required review step alongside `npm run precommit` — precommit verifies correctness, branch-review's multi-agent pass catches defects and design issues a static check won't. It replaces the old `/review` and pre-PR `/code-review` steps, which Claude cannot invoke (`/code-review` remains available for humans to run as an extra independent engine).
- **Record project learnings here, not in agent memory**: when you discover something non-obvious about this system — a trap, a subtle contract, a verification technique that actually works, a symptom and what it means — write it into this file (or the closest relevant doc) as part of the same change. Do not stash it in an agent's private memory: teammates and other agents cannot read it, nobody reviews it, and it silently goes stale as the code moves. Guidance in the repo is versioned, reviewed, and inherited by every future session. Keep what you add generic, per the public-examples rule above: describe the mechanism and the failure mode, never the deployment, hostnames, or venue details — deployment-specific facts belong in the private inventory repository instead.
- **Update README.md**: Ensure that you consider any updates to user facing documentation as part of any changes.
- **Inline-script classifiers are tech-generic only**: matchers in `src/utils/script/inline.ts` classify a technology (framework/vendor-emitted snippets), never a site. Only add one when the snippet is attributable to the framework or vendor's own source or documentation — cite the evidence in the matcher's comment. Anything application-specific belongs in the target's inventory entry (the inventory workflow generates an anchored content-snippet matcher for unrecognised inline scripts, combined with the initiator host when the initiator URL is available).
